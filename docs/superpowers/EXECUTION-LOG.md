## 执行中发现的计划缺陷

计划由 AI 撰写,执行中被实现者与评审者抓出 4 处错误。记录于此,因为它们说明了哪类假设不可靠:

1. **主题检测脚本位置**——Step 2 散文写「必须在 `<head>` 中同步执行」,Step 5 的代码却放在 `<body>`。实现者未擅自改,而是上报矛盾;评审驳回了"本机实测无闪烁"的论证,理由是测试条件(localhost、单个 TCP 包、无节流)恰恰最容易掩盖该 bug。
2. **RSS 条目计数**——`grep -c '<item>' dist/rss.xml` 恒返回 1,因为 `@astrojs/rss` 输出单行 XML。正确写法是 `grep -o '<item>' | wc -l`。
3. **Pagefind 组件 API(两处,只抓到一处)**——计划的 `Search` 用法对不上 `astro-pagefind@2.0.1`:import 需带 `.astro` 扩展名(exports map 无扩展名回退),且 `id`/`uiOptions` 属性不存在。Task 7 修了 import,**但没回头重查该包的其他假设**,于是 CSS 变量契约(`--pagefind-ui-*` vs 实际的 `--pf-*`)漏网,直到最终评审才发现——那段主题化代码看起来正确但完全不生效,暗色模式下搜索框是白底。
   > 教训:当计划被证明对某个依赖的 API 判断有误时,应重查它对**同一依赖**的所有其他假设,而不只修失败的那一行。
4. **`originalAuthor` 被描述为 schema 强制**——实际是 `.optional()`。Zod 无法表达「仅当转述他人作品时必填」(需额外的判别字段)。同一错误在文档中有四处表述,分三轮才扫干净。
