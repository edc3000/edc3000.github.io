01 · 核心问题

Kaggle 项目最容易坏在模型之外

多日竞赛不是一串互不相关的训练命令。验证协议、实验血缘、云端版本、预测文件、提交配额和榜单反馈彼此依赖； 只要其中一环没有留下可核对的事实，后面的优化就可能建立在错觉上。

!

Kaggle Autopilot 优化的是决策过程，而不是某个固定模型。 它把开放式竞赛压成有入口、有状态、有证据门、有恢复点的闭环，让 Agent 能自主推进，又不能用猜测替代事实。

01 · 验证错位

离线涨分可能只是泄漏

随机切分会掩盖实体、时间、空间、来源或近重复边界。项目要求先解释隐藏测试如何生成，再决定 splitter。

02 · 无法归因

改了很多，却不知道什么有效

每个实验必须登记父方案、单一核心假设、变化轴和失败条件；复合改动还要留下可拆解的 ablation。

03 · 假完成

Notebook 完成不等于提交有效

云端运行完成、输出文件有效、平台接受提交、最终得到分数是四种独立证据，不能相互代替。

04 · 重复消耗

两个文件名可能是同一份预测

文件 SHA-256 识别字节，语义预测指纹识别内容；换文件名或浮点格式，仍会被判定为历史重复。

05 · 榜单追逐

一次公开榜波动不够证明方向

榜单只用于校准与证伪，还要联合 CV、子群稳定性、日志、预测差异与数据偏移进行归因。

06 · 跨天失忆

对话记忆不是项目状态

事实、假设、命令、结果和阻塞都写进比赛目录。恢复时先读磁盘和平台现状，再从首个未完成状态继续。

02 · 协作结构

Agent 负责判断，确定性工具负责守门

这个仓库并没有实现一个通用训练器。核心是三层分工：Skill 规定判断顺序，Kaggle 与检索工具接触动态世界， 三个标准库脚本处理可重复验证的初始化、提交审计和配额计算。所有结果最终回到项目文件，成为下次运行的起点。

competition.yaml

机器事实与当前状态

保存比赛状态、提交模式、指标方向、数据 schema、验证门槛、配额和资源策略。未知值保持 null 或 unknown。

competition_monitor.md

给人读的中文时间线

记录当轮事实、诊断、候选、云端运行、提交、归因、阻塞与下一步，避免只剩下无法解释的分数。

experiments.csv

实验与提交血缘

把父实验、假设、验证、证据等级、预测指纹、kernel 版本、提交引用、结果与决策连在一行。

validation_profile.md

验证协议的理由

从数据生成机制、泄漏边界和官方指标出发，写清切分、lockbox、OOF 与稳定性检查的职责。

public_intel.md

公开证据的适用范围

保存来源、访问时间、数据版本、关键假设和复现状态；榜单声称不能直接升级为本地事实。

runs/ · oof/ · preds/ · submissions/

版本化运行产物

保存日志、OOF、预测和实际提交文件，让某个分数能回到当时的代码、配置和预测内容。

03 · 一次完整运行

一个 Loop 对应一个提交日

“用满额度”不是先决定提交几次，再随便找文件补齐。系统先同步旧结果、刷新当前目标，再产生和验证候选； 只有通过证据、云端与输出检查的不同预测，才会进入当天的批次。结果完成归因并写回之后，这一轮才算结束。

阶段 01

先确认今天究竟还能做什么

系统读取磁盘状态和 Kaggle 当前状态，结清所有未决结果，再决定当前重置窗口中的剩余额度。配额没有权威数字时，这一阶段直接阻断。

读取competition.yaml、提交历史、kernel 状态、比赛规则
修改当前状态、动态目标、待决条目、配额窗口
输出可用额度与首个未完成状态
阶段 02

把现象变成可证伪假设

离线分数、子群稳定性、云端日志和榜单变化放在一起解释；公开方案只转化为最小可验证实验，不直接当作正确答案。

读取历史实验、公开证据、日志、CV 与榜单响应
修改当前诊断、父实验、单一变化轴与失败条件
输出已登记、可归因的候选实验
阶段 03

在可信验证上晋级，并到真实云端复现

候选先证明本地验证没有明显泄漏，再根据风险追加多折、时间或群组 holdout、bootstrap 等证据，最后运行 Kaggle 版本并保存确切产物。

读取validation_profile.md、数据、配置与代码版本
修改证据等级、fold/seed/subgroup 结果、云端版本
输出日志、OOF、预测文件与云端复现证据
阶段 04

只让结构正确、内容独特的预测进入批次

候选要同时满足 sample submission 合同、数值有效性、ID 对齐和历史语义去重；批次还要考虑相关性、稳定性与失败风险。

读取sample、candidate、experiments.csv 与剩余额度
修改预测指纹、审计结果、候选决策
输出可提交且互补的候选批次
阶段 05

提交之后仍要等到结果能被解释

系统记录提交引用并轮询结果。分数、失败或延迟都要回写；只有实验、预测、平台结果和最终决策连起来，一轮才真正关闭。

读取合格批次、平台状态、当前目标
修改提交引用、公开/私榜分数、冻结或保留决策
输出已归因结果，或明确的 WAIT_RESULTS / BLOCKED
04 · 提交资格

提交键前有三道门

证据门判断“这个候选值不值得交”，审计门判断“这份文件能不能交”，配额门判断“现在还可不可以交”。 三者检查的对象不同，任何一项失败都不能用另外两项补偿。

GATE 01

证据门：候选有多可信

从 smoke test 到真实 Kaggle 云端复现逐级积累证据。正式提交必须同时通过 E0 与 E5。

  • 中间最低等级写在比赛配置里
  • 验证设计随数据生成机制变化
  • 不把榜单分数当唯一训练信号
GATE 02

审计门：文件是否满足合同

audit_submission.py 对照 sample 检查表头、行数、ID、顺序、空值、有限数值和历史预测指纹。

  • 文件 hash 识别字节是否相同
  • 预测 hash 识别语义是否相同
  • 非零退出码直接阻断提交
GATE 03

配额门：当前窗口还剩多少

quota_status.py 使用已验证的每日上限、重置时区、重置小时和 Kaggle 提交历史计算剩余数量。

  • 不默认假设“每天固定几次”
  • 同时支持 CSV 与 JSON 历史
  • 配额未知时硬失败，不静默猜值
E0代码、数据、指标和提交结构 smoke test
正式提交必需
E1一个无泄漏验证切分
E2多折、多种子、多实体或多窗口
E3hidden-like、out-of-time、group holdout 或 lockbox
E4cross-fit、bootstrap、子群、偏移与稳健性
E5Kaggle 云端完整复现并通过输出审计
正式提交必需
证据等级不是固定考试题。 E2–E4 的具体检查由 validation_profile.md 定义：时间任务看 out-of-time，实体冷启动看 group holdout，分布偏移任务看 domain/source 稳定性。
05 · Running Example

跟着一场直传文件比赛走一遍

项目是通用 Skill，没有绑定某场真实比赛。下面严格采用 README 提供的 <competition-slug>、 exp_042.csv 与审计结果，展示一条不虚构分数的端到端路径。

STEP 01 · 用户触发

授权的是完整提交 Loop，不是单次实验

用户明确要求创建并推进比赛，同时按当天最大提交次数完成一轮。这个授权允许系统对所有合格候选连续提交，但不允许降低证据标准凑额度。

使用 kaggle-autopilot 创建并自动推进 <competition-slug>，
按当天最大提交次数完成一个实验与提交 loop。
STEP 02 · 初始化持久化状态

先创建事实容器，再去填事实

init_competition.py 校验 slug、时区与配额参数，创建比赛目录和模板；目标已存在时默认拒绝覆盖，显式使用 --allow-existing 也只补缺失文件。

python scripts/init_competition.py --workspace . \
  --slug <competition-slug> --title "<competition title>" \
  --submission-mode unknown

STEP 03 · 发现与验证设计

从隐藏测试机制倒推本地验证

Agent 通过官方来源确认比赛状态、指标方向、提交模式和配额，再审计实体、时间、空间、来源与近重复边界。 只有这些事实写入 competition.yaml 与 validation_profile.md 后，本地分数才有资格成为候选证据。

若是 IID检查类平衡、尾部稳定性与重复簇
若有实体或时间按 group 或未来边界隔离
若测试机制特殊增加 hidden-like 与 lockbox 反证
STEP 04 · 候选从云端回来

exp_042.csv 先过输出审计

配额来自配置和提交历史，不来自记忆

脚本把提交时间转换到官方重置时区，只统计当前窗口。若每日上限仍为 null，它返回错误并阻断后续提交。

python scripts/quota_status.py \
  --config competitions/<slug>/competition.yaml \
  --submissions exported-submissions.csv
STEP 06 · 提交、等待与归因

这条示例不会编造一个榜单分数

合格且互补的候选进入批次，提交引用写进 experiments.csv。平台若立即评分，就联合离线证据完成归因； 若评分延迟，就进入 WAIT_RESULTS；若认证、规则或比赛状态阻断，就写入 BLOCKED 和恢复条件。

已评分记录分数、归因与保留/冻结决策
评分延迟保存提交引用，从 WAIT_RESULTS 恢复
平台阻断保存原始错误与明确恢复条件
06 · 可迁移的设计判断

这些选择换来了什么，又放弃了什么

项目的价值不只在操作顺序，更在它对可靠性做出的取舍。下面每张卡的折叠态已经给出判断；展开后可以查看代价和失效边界。

磁盘事实优先于聊天记忆 恢复依据是配置、台账和平台状态，因此跨天与跨会话仍能继续。
对话上下文→ 选择 →持久化比赛目录

得到：每个结果都能回到实验、预测和云端版本；上下文被压缩或会话结束，也不会丢掉状态。

放弃：每轮都要维护多份产物，短期看比随手记在对话里更重。对于一次性、无提交、无需恢复的探索，这套台账可能显得过度。

未知值硬失败，不填经验默认值 提交模式、指标方向和配额没有证据时保持 unknown/null。
先猜一个常见值→ 选择 →等待权威事实

得到：不会因“通常每天几次”或“看起来像文件比赛”做出不可逆的平台操作；失败发生在提交之前。

放弃：发现阶段可能更慢，也更容易停在硬阻塞。若平台能稳定提供结构化权威元数据，这一步可以自动化，但仍不应把猜测伪装成事实。

真实云端运行优先于复制产物 本地成功和旧输出都不能证明当前 Kaggle 版本可复现。
沿用已有输出→ 选择 →绑定当前 cloud run

得到：依赖、路径、数据源、runtime 与输出文件都在真实环境中被验证；kernel 完成、输出有效、提交接受和评分仍分别跟踪。

放弃：增加等待和云端资源成本。仅做本地方法探索时可以暂不追求 E5，但一旦正式提交，项目把 E5 设为必要条件。

正交批次优先于一排高分近邻 提交批次覆盖不同风险轴，减少多个名额押在同一个误判上。
按 CV 排名前 N→ 选择 →质量门槛 + 预测互补

得到：批次同时包含稳定父方案、结构改进、独立表示或低相关融合，让有限的榜单反馈更有诊断价值。

放弃：要额外计算相关性、差异行占比与预期分歧来源。配额非常少时，保守候选可能比追求覆盖更重要。

标准库脚本优先于丰富依赖 三个守门脚本无需安装依赖，减少陌生 Agent 环境里的启动失败。
依赖完整工具栈→ 选择 →Python 标准库

得到：初始化、CSV 审计、哈希和时间窗口计算更容易在 Codex、Claude Code 与 Kaggle 周边环境中复用。

放弃：例如配额脚本只能直接读取 JSON 兼容 YAML；遇到更完整的 YAML 语法时，需要环境中已有 PyYAML。零依赖换来的是接口克制，不是无限格式支持。

失败方向被冻结，但不会被抹掉 重复可信评估无收益时记录失败墓地，只有新证据才能重启。
删除或随时重试→ 选择 →冻结并写明重启条件

得到：失败本身成为可复用证据，团队不会因为模糊的榜单波动重复消耗算力和提交额度。

放弃：冻结判断如果建立在不可信验证上，会把好方向过早关掉。因此项目要求同时保存失败实验、具体证据和允许重启的条件。

07 · 适用边界

自动推进不等于无限权限

系统对确定性故障可以修复，对暂时性平台错误可以有限重试，但涉及用户法律行为、凭据、付费、未知配额或失效输出时必须交还控制权。 这个边界使“自主使用额度”不会滑向“未经确认做任何事”。

必须停止并说明恢复条件

  • 规则尚未接受：接受规则是用户本人的法律行为
  • 认证失败：不能猜测、打印或代填凭据
  • 比赛关闭或配额未知：继续提交没有合法安全的前提
  • 需要付费资源：花费需要新的用户授权
  • 数据不可用或输出合同失败：继续运行只会制造假证据

可以在范围内恢复

  • 修复确定性的本地命令错误后重跑
  • 暂时性网络或平台错误进行有限退避
  • kernel 失败后先读日志，改变代码或环境再创建新版本
  • 评分延迟时保存 WAIT_RESULTS 并继续轮询

它明确不会做

  • 代替用户接受比赛规则
  • 处理验证码或绕过访问控制
  • 暴露凭据或把凭据写进日志
  • 承诺任何奖牌、排名或特定比赛结果
  • 把小公开榜变成唯一优化数据集
最终判断

适合需要多日运行、云端执行、有限提交配额和完整实验归因的竞赛；如果只是一次性本地试验，不需要提交或恢复，这套状态机的维护成本可能高于收益。
