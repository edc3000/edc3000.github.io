核心结论
它真正优化的不是 HTML 的“好看程度”，而是读者从陌生材料走到正确心智模型的路径。

视觉组件只是末端手段。五份契约减少方向性返工，材料驱动的 section 保住原作逻辑，四层验证拦住语法、布局和理解层面的失败。

01 · 问题

普通“可视化解读”为什么经常只剩外观

常见做法直接从“页面应该放哪些组件”开始。这样生成出的内容可能很丰富，却让读者自己承担组织信息的工作：找主线、补概念边界、猜流程、再判断页面是否可信。

01 模板先于材料

先决定卡片、时间线和总结章，再把内容塞进去。

02 主线被切碎

关键论证散在折叠卡片里，读者必须点击拼图。

03 概念边界漂移

相邻术语被翻成同一个词，流程对象也说不清。

04 交付未经运行

静态看似完整，JS、图片或窄屏布局却可能已经失效。

这个 skill 的解决方式是把问题前移：页面结构不再是起点，而是理解材料之后得到的答案。它要求正文承担主线，图只负责把抽象关系具体化，卡片只负责加深已经建立的理解。把所有折叠区域收起，读者仍应能从头到尾复述核心论证。

02 · 机制

五份契约与四层验证，是两根承重柱

七步流程里，只有两个环节不能靠经验略过：写作前必须停下来让用户确认方向，交付前必须让页面真正运行起来。一个拦截“做错页面”，另一个拦截“页面做坏了”。

写作之前

契约把模糊要求变成可检查的理解目标

读者契约防止解释密度失衡；术语契约固定概念边界；数据流契约强迫作者说清读、改、写；贯穿例子把抽象流程落到真实对象；主线契约决定哪些内容值得默认展开。

交付之前

验证把“看起来完成”变成“有证据完成”

静态检查抓字符串、外链和 DOM 结构；运行时检查打开所有交互并扫三档宽度；内容检查回对原材料；读者理解检查确认读者能说出对象、状态和边界。

五份契约先对齐，HTML 才能开工

读者 什么可直接说，什么必须解释
术语 3–8 个骨干概念及其边界
数据流 每阶段读取、修改与输出什么
贯穿例子 真实输入如何一步步成为产物
主线 全文共同回答的一个问题
确认闸门 契约写完必须暂停。用户明确同意后，才进入 section 与组件设计。
03 · 数据流

一次任务从陌生材料走到可交付页面

下面的七个节点不是抽象标签：每一步都写明它读取什么、改变什么、留下什么。点击阶段可查看状态变化；不点击也能从这段主线看懂：材料先被分类和取材，契约确认后才设计与写作，最后通过验证进入交付。

先判断输入形态

取材不是全文扫一遍，而是按输入类型找主线素材

URL 抓正文，论文优先 HTML 版；本地项目先看 README、目录、入口、配置和示例。动手画图前先找原作者已有的图。

并列关系用卡片，链式关系用流程图，层级关系用树；动画只有在展示真实状态变化时才成立。一屏至多一个视觉锚点。

04 · 文档架构

一个入口负责原则，九份 reference 负责判断

当前仓库没有构建脚本和固定 HTML 骨架。SKILL.md 只保存不会随材料变化的原则；真正需要按场景展开的判断被拆到九份 reference，避免入口文件膨胀成难以执行的长清单。

SKILL.md · 执行入口 硬约束、默认读者、七步流程与路由规则

先把方向定准

输入与契约

contracts.md固定五份契约、section 职责与标题边界

让材料决定叙事

三条专项路线
paper.md围绕问题、方法和少量证据精读单篇论文
survey.md先建 taxonomy，再按子问题递归展开关键工作
project.md从真实运行、模块角色和设计取舍理解项目

把产物做对

表达与质量控制
visual-patterns.md图形选择、配色、响应式与交互实现陷阱
writing-style.md中文解释密度、概念边界与不过度表达
verify.md静态、浏览器、内容与读者理解四层检查
anti-patterns.md40 条真实失败模式，写前与验收时各扫一遍
README.md 面向使用者解释安装、调用、流程与设计来历；它是入口说明，不参与运行时依赖。

职责关系：入口决定“必须遵守什么”，输入与专项文档决定“这次该怎么讲”，表达与验证文档决定“怎样把它可靠交付”。

这个例子也暴露了一个重要边界：skill 的“程序状态”不在某个数据库里，而在对话确认、读取到的材料和生成中的 HTML里。下一次运行不会自动继承本次状态；除非用户提供当前对话结论，否则它会重新取材和定契约。

06 · 设计取舍

它用更强的过程纪律，换取更少的模板偏差

这套设计不是“免费得到更好页面”。它有意放弃固定骨架、第三方运行时和一次生成到底的速度，换来内容适配、离线可靠与较少的方向性返工。

不保留固定 HTML 骨架

section 与视觉结构能真正服从材料，不会把每份输入都压进同一模板。

一致性不再由代码保证，而要依赖契约、规则执行和验收纪律。

单文件、零运行时依赖

页面可离线打开、容易分享，也不会因为 CDN 失效而老化。

Mermaid 等源码必须转译；复杂图和交互需要手工实现并验证。

契约后强制暂停

在低成本阶段发现读者、术语或主线偏差，避免整页返工。

多一次人机往返，不适合只求极速草稿的场景。

运行时验证不可省略

能发现 JS 静默失效、展开内容截断、外部请求与窄屏溢出。

需要可用浏览器环境；没有时必须降低验证等级并如实披露。

这一取舍有版本证据。 2026-08-13 的重构提交 7615f01 ↗ 删除了固定 skeleton、组件资产、构建脚本与测试目录，新增工程项目专项和完整 reference。当前设计明确选择“规则驱动的现场生成”，而不是“模板驱动的机械拼装”。

07 · 边界

什么时候不值得动用这套完整流程

它最适合“材料复杂、理解成本高、产物需要独立分享”的任务。若核心需求不是教学阅读，强行使用五份契约与四层验证反而会增加不必要的过程成本。

适合使用

  • 论文、综述或工程项目需要被真正讲清楚
  • 读者需要顺着主线建立心智模型
  • 产物要离线保存、独立分享或长期归档
  • 愿意为契约确认和浏览器验收多花一轮时间

换一种产物更合适

  • 只需要一页速记、会议摘要或原文摘录
  • 需要实时数据、后台接口或复杂应用状态
  • 页面必须进入既有设计系统和组件构建链
  • 无法取得材料、也无法验证关键事实与运行状态
