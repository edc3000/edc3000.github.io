pi：一个可扩展 coding agent harness 的内部结构

仓库 github.com/earendil-works/pi ↗ 语言 TypeScript（Node ≥ 22.19） 规模 11 个包 · 673 个源文件 · 约 17.4 万行 最后提交 2026-10-15

核心结论

  1. 三层分工。pi-ai 把 10 种模型 API 统一成一套流式事件；pi-agent-core 只做「调模型 → 执行工具 → 再调模型」的循环，不存盘、不碰文件系统；pi-coding-agent 提供工具、会话存储、压缩、扩展和界面。
  2. 层与层之间靠 hook 连接。agent-core 留了 prepareRequest、beforeToolCall、afterToolCall、finishTurn、prepareNextTurn 几个口子；会话持久化、自动压缩、扩展拦截工具调用，都是 coding-agent 往这些口子里填实现。
  3. 以磁盘上的 JSONL 会话树为准。每次请求模型之前，都从当前分支重新算一遍要发送的上下文。所以分支、压缩、上下文编辑都只需要「追加一条记录」，原始历史永远不改。

pi 想做的事

README 对自己的定位是 a minimal, extensible agent harness that you can make your own：一个最小、可扩展、可以改成自己想要样子的 agent harness。它有意不内置 sub-agent 和 plan mode，想要的话让 pi 自己写一个，或者装一个别人写好的 Pi package。

「可扩展」落到代码上有两层意思：

  • 同一套核心，多种入口。终端交互（interactive）、一次性输出（print）、事件流输出（JSON）、stdin/stdout 上的 JSONL 协议（RPC）、进程内调用（TypeScript SDK），都共用同一个 AgentSession 和同一份会话文件。
  • 行为可以从外部改。扩展（extension）是加载进 pi 进程的 TS 模块，能注册工具、命令、快捷键、模型提供方、事件处理器和 UI 组件；skill、prompt 模板、主题是另外几类可分发资源。

所以读这个仓库要回答的问题是：pi 怎么把一个与模型无关、本身不保存状态的 agent 循环，做成一个可持久化、可分支、可扩展的 coding agent？下面先看模块怎么切，再跟一个真实请求走一遍。

pi 交互模式的截图：启动时列出加载到的资源，下方是一次正在进行的 run。（来自仓库 packages/coding-agent/docs/images/interactive-mode.png）
  • [Context]：被读进 system prompt 的上下文文件，这里是 ~/.pi/agent/AGENTS.md。
  • [Skills] / [Prompts]：skill 只把名字和描述放进 prompt，完整说明在模型需要时才读；prompt 模板在输入框里用 /名字 展开。
  • [Extensions]：已加载的扩展。截图里的 subagent 就是用户自己装的扩展，pi 本身不带 sub-agent。
  • 工具块：read docs … 和 $ pwd && find … 分别是 read 工具和 bash 工具的调用，由各自的渲染器（core/tools/renderers/）画出来，默认截断，ctrl+o 展开。
  • 底部状态栏：token 用量、缓存命中率、费用、上下文占用（9.7%/272k），以及当前模型和 thinking 级别。

三个包各管什么

仓库是一个 monorepo，但对理解 agent 本身，只需要盯住三个包。它们是严格的单向依赖：上层调用下层，下层不知道上层的存在。

依赖方向只有自上而下一条：界面 → AgentSession → Agent → pi-ai。
  • 界面层：只负责把用户输入交给 AgentSession.prompt()，再把 AgentSession 发出的事件画出来或序列化输出。五种入口共用同一个 session，所以行为一致。
  • AgentSession：整个 coding agent 的中枢。构造时订阅 Agent 事件（用来存盘），并调用 _installAgentToolHooks、_installAgentRequestProjection、_installAgentNextTurnRefresh、_installAgentBoundaryHooks 把自己的逻辑装进 Agent。
  • Agent / runLoop：只管消息数组、两个排队消息的队列和循环本身。它通过 streamFn 调模型，通过 AgentTool.execute 调工具，二者都由上层注入。
  • pi-ai：把每家 API 的 SSE/流式响应翻译成同一套 AssistantMessageEvent。api（线上协议）和 provider（厂商）是两个维度：DeepSeek、Groq 等都复用 openai-completions 协议。
  • 一句话：越往下越通用，越往上越「coding agent」。

从回车到改好文件：一次 run 的完整路径

先把两个反复出现的词定下来：

turn：模型回复一次，加上执行这次回复里发起的所有工具调用。
run：从一次 prompt() 开始，到发出 agent_end 事件为止的全过程。只要模型还在调用工具，一个 run 就会连续跑多个 turn。

下面用一个具体请求走一遍：用户在 /work/demo 目录启动 pi，输入「修复 src/math.ts 里 add 的 bug」。文件里 add 写成了 return a - b;。这个 run 会跑 3 个 turn：读文件、改文件、回复文字。右侧是会话文件 ~/.pi/agent/sessions/--work-demo--/<时间>_<uuid>.jsonl 的逐步变化（行内容按 docs/session-format.md 的格式构造，省略了时间戳和 usage 等字段）。

    按顺序播放本步的调用；切换步骤会自动播放
    会话文件（JSONL，每行一条 entry）

      把这 9 步压成一句话：Agent 在内存里推进循环；每条消息一结束，AgentSession 就把它追加进 JSONL；每次请求模型前，又从 JSONL 的当前分支重新算出上下文。内存里的 messages 只是工作副本，磁盘上的会话树才是依据。后面几节分别展开这条路径上的四个环节：循环本身、模型调用、工具调用、会话存储。

      runLoop 的两层循环：turn、steering 与 follow-up

      agent 一边跑，用户一边还能继续打字。pi 把这时输入的消息分成两种，放进 Agent 的两个队列：

      • steering（运行中按回车）：当前 turn 的工具执行完后插入，模型下一次回复就能看到。用来纠偏，比如「别改测试文件」。
      • follow-up（运行中按 Alt+Enter）：等 agent 原本要停下的时候才插入，相当于排在后面的下一个任务。

      这两种时机正好对应 runLoop 的两层 while：内层只要还有工具调用或 steering 消息就继续发请求；内层退出后，外层再检查 follow-up 队列，有就把它当作新输入重新进入内层。

      内层循环按「注入消息 → 准备请求 → 调模型 → 执行工具 → 结束 turn」转圈；外层只在内层要停时检查 follow-up。
      • 注入排队消息：同时会调用 declareToolChanges。如果可用工具集合和对话里已经声明过的不一致，就插入一条带 toolsAdded / toolsRemoved 的 system 消息，让模型知道工具变了。
      • prepareRequest：agent-core 只负责调用，内容由 AgentSession 填写：从会话树重建 messages，必要时先压缩，virtual model 在这里路由到具体模型。
      • streamAssistant → executeToolCalls：模型消息里有工具调用才进入执行；如果 stopReason 是 length，所有工具调用直接判为失败、不执行（原因见「设计取舍」一节）。
      • finishTurn：返回 {action:"end"} 可以强行结束 run，返回 continue 可以在没有新消息时再要一次回复。扩展的 turn_end 处理就挂在这里。
      • 两个虚线箭头：内层回到「注入消息」，外层回到内层起点，分别对应 steering 和 follow-up 的插入时机。
      runLoop 主体（节选）两层 while 的骨架，略去了 prepareNextTurn 对模型和 thinking 级别的更新 · packages/agent/src/agent-loop.ts:163

    // 1. 把 steering / follow-up 消息推进上下文（并声明工具变化）

    // 4. 执行工具；输出被截断时不执行

      : await executeToolCalls(currentContext, message, config, signal, emit);

    // 5. turn 结束，取下一批 steering
    const decision = await config.finishTurn?.(lastCompletedTurn, signal);
    if (decision?.action === "end") { /* agent_end */ return; }
    pendingMessages = (await config.getSteeringMessages?.()) || [];
  }
  const followUps = (await config.getFollowUpMessages?.()) || [];
  if (followUps.length > 0) { pendingMessages = followUps; continue; }
  break;
}

      两个队列默认都是 one-at-a-time 模式：每次只取队首一条（PendingMessageQueue.peek），用户连敲三条 steering，会分三个 turn 依次注入；设成 all 则一次全部注入。中断（Esc）时，Agent.abort() 触发 AbortController，信号一路传到模型请求和每个工具的 execute，排队消息被退回到输入框。

      pi-ai：一套事件对接 10 种 API

      pi-ai 区分两个经常被混用的概念：

      api：线上协议，例如 anthropic-messages、openai-completions、openai-responses、google-generative-ai、bedrock-converse-stream，内置 10 种，每种一个实现文件 api/*.ts。
      provider：厂商或网关，例如 anthropic、deepseek、groq、openrouter，providers/ 下有 40 多家。很多 provider 共用同一种 api，比如 DeepSeek 走 openai-completions。

      每个 Model 同时带着 api 和 provider 两个字段。stream() 按 model.api 在一个 Map 注册表里找实现，按 provider 找 API key。所有实现都必须产出同一套事件：

      // packages/ai/src/types.ts:806
type AssistantMessageEvent =
  | { type: "start"; partial }
  | { type: "text_start" | "text_delta" | "text_end"; ... partial }
  | { type: "thinking_start" | "thinking_delta" | "thinking_end"; ... partial }
  | { type: "toolcall_start" | "toolcall_delta" | "toolcall_end"; ... partial }
  | { type: "done";  reason: "stop" | "length" | "toolUse" | "deferred"; message }
  | { type: "error"; reason: "aborted" | "error"; error };

      这里有一个细节：每个事件都附带 partial，也就是截至此刻拼好的完整 AssistantMessage，而不只是增量。streamAssistantResponse 收到事件后直接用 partial 替换上下文里的最后一条消息，再发出 message_update。消费方（TUI、扩展、RPC 客户端）不需要自己拼增量，任何时刻拿到的都是可以直接渲染的完整消息。

      注册表是公开的：扩展可以用 registerApiProvider 注册新协议，测试用 registerFauxProvider 注册一个按脚本回放响应的假 provider。仓库规则要求 test/suite/ 下的测试全部走这个 faux provider，不调用真实 API、不花 token。

      一次工具调用经过的步骤

      模型的一条回复里可能有多个工具调用。executeToolCalls 默认并行执行；只要其中某个工具声明了 executionMode: "sequential"，整批改为串行。每个调用都要走同一条流水线（packages/agent/src/agent-loop.ts:708–900）：

      ① 按名字找工具在 context.tools 里查找不到 → 「Tool X not found」
      ② prepareArguments修正模型的不规范参数抛错 → 错误结果
      ③ schema 校验validateToolArguments不合法 → 错误结果
      ④ beforeToolCall扩展的 tool_call 事件block → 错误结果
      ⑤ execute真正执行，可用 onUpdate 推送进度抛异常 → 错误结果
      ⑥ afterToolCall扩展的 tool_result 事件、图片缩放可改写 content / isError

      每一步失败都不会抛出到循环之外，而是变成一条 isError: true 的 toolResult 交给模型。模型看到「参数校验失败」或「oldText 不唯一」之后会自己修正重试，run 不会因此中断。并行执行时各调用独立完成，但最终 toolResult 消息按模型发出调用的顺序写入，transcript 的顺序始终稳定。

      以 edit 工具为例

      内置工具在 packages/coding-agent/src/core/tools/，每个工具一个文件。edit 的 execute（edit.ts:159）把上面第 ⑤ 步展开成这样：

      1. 参数兼容（第 ② 步，prepareEditArguments）：注释写明有些模型（Opus 4.6、GLM-5.1）把 edits 当 JSON 字符串发，有些发单个对象而不是数组，还有旧格式的顶层 oldText/newText，全部先规整成 edits: [...]。
      2. 进入文件写队列：withFileMutationQueue(absolutePath, …)，同一个文件（按 realpath 判断）的写操作排队，不同文件照常并行。
      3. 规范化：去掉 BOM、记下原换行符、统一转成 LF 再匹配，写回时还原。模型给的 oldText 里不会有 BOM 和 \r。
      4. 匹配（edit-diff.ts:207 fuzzyFindText）：先精确匹配；找不到再做 NFKC 规范化、去行尾空白、把弯引号和长破折号换成 ASCII 后模糊匹配。每段 oldText 必须唯一且互不重叠，否则报错让模型重发。
      5. 写回并返回：content 只给模型一句「Successfully replaced N block(s)」，details 带 diff 和 unified patch 给 TUI 渲染。

      文件读写都经过一个 EditOperations 接口（readFile / writeFile / access），默认实现是本地 fs。换一个实现就能把工具转到 SSH 或容器里执行，工具逻辑一行不改。bash、read 等工具也是这个模式。工具输出统一按 2000 行或 50KB（先到者为准）截断，大约一万多个 token。bash 截断时会把完整输出写进临时文件，并把路径告诉模型。

      同一文件串行、不同文件并行的写队列每个文件一条 Promise 链；注册本身也排队，避免两个调用同时读到空队列 · core/tools/file-mutation-queue.ts:32 
      export async function withFileMutationQueue(filePath, fn) {
  const registration = registrationQueue.then(async () => {
    const key = await getMutationQueueKey(filePath);       // realpath，软链接指向同一文件也算同一个
    const currentQueue = fileMutationQueues.get(key) ?? Promise.resolve();
    let releaseNext;
    const nextQueue = new Promise((r) => { releaseNext = r; });
    const chainedQueue = currentQueue.then(() => nextQueue);
    fileMutationQueues.set(key, chainedQueue);                 // 后来者排在我后面
    return { key, currentQueue, chainedQueue, releaseNext };
  });
  registrationQueue = registration.then(() => undefined, () => undefined);
  const { key, currentQueue, chainedQueue, releaseNext } = await registration;
  await currentQueue;                                          // 等前一个写完
  try { return await fn(); }
  finally {
    releaseNext();
    if (fileMutationQueues.get(key) === chainedQueue) fileMutationQueues.delete(key);
  }
}

      会话树、projection 与压缩

      会话文件是 JSONL，第一行是 header，之后每行一条 entry。每条 entry 带 id 和 parentId，所以整个文件是一棵树，不是一条链。SessionManager 在内存里维护一个 leafId，指向当前所在的 entry：

      • 追加：appendMessage 以 leafId 为父节点新建 entry，然后把 leafId 移过去（session-manager.ts:1204）。
      • 分支：branch(id) 只是把 leafId 改回某条旧 entry（:1579）。之后的追加自然长出一条新枝，旧枝原样留在文件里。
      • 当前分支：getBranch() 从 leafId 沿 parentId 走回根，再反转（:1469）。

      entry 不只有消息，还有 model_change、thinking_level_change、compaction、branch_summary、context_edit、custom（扩展状态，不进上下文）、custom_message（扩展注入、进上下文）、label 等。模型切换、压缩这类操作都记成树上的节点，所以回到任何一个节点，当时的模型和上下文都能还原出来。

      /tree 命令看到的会话树：一个文件里有多条分支，可以跳到任意节点继续。（来自仓库 packages/coding-agent/docs/images/tree-view.png）
      • 竖线和拐角：表示 parentId 关系。同一个父节点下的多个 user: 是从同一处分出来的不同分支。
      • 灰色方括号行（[bash: git status]、[read: …]）：assistant 消息里的工具调用。树里把它们折成一行，方便扫读。
      • assistant: (aborted)：被 Esc 中断的回复也是一条正常 entry，stopReason 为 aborted，之后的对话照样接在它后面。
      • 底部 › 标记和 (2759/2759)：当前选中的节点，也就是 leafId 所在的位置，以及节点总数。选中另一个节点再继续对话，就是一次 branch()；选中 user 消息时分叉点是它的父节点，消息文字回到输入框供修改。
      • 切换分支时可以让模型把离开的那条分支总结成一条 branch_summary entry，挂在新分支上，旧分支里学到的东西不会丢。

      projection：每次请求前重新算上下文

      发给模型的 messages 不是一直在内存里累加的，而是每次请求前由 buildSessionProjection（session-manager.ts:543）从树上重新计算：

      1. 从 leafId 走回根，得到当前分支的 entry 列表；
      2. 找到分支上最新的 compaction entry：它之前、firstKeptEntryId 之前的 entry 全部换成这条压缩摘要；
      3. 套用 context_edit：某条 entry 被编辑过就用替换内容，replacement: null 则直接去掉；
      4. 把每条 entry 转成消息，再经 convertToLlm（core/messages.ts:148）把 pi 自有的消息类型（! 执行的 bash 输出、扩展消息、压缩摘要、分支摘要）转成模型认识的 user 消息。

      AgentSession 在 prepareRequest 和 prepareNextTurn 两个 hook 里都调用它，用结果覆盖 Agent 内存里的 messages。这就是为什么压缩、编辑、分支都不需要去改 Agent 的状态：改树，下一次请求自然就看到新上下文。

      压缩：追加摘要，不删历史

      触发条件是 contextTokens > contextWindow − reserveTokens，reserveTokens 默认 16384，给模型的回复留空间。拿 200k 上下文窗口的模型来说，大约到 18.4 万 token 时触发。触发后：从分支末尾往前累加 token，直到攒够 keepRecentTokens（默认 20000）定出切点；切点之前的消息交给模型生成结构化摘要；最后追加一条 CompactionEntry { summary, firstKeptEntryId, tokensBefore }。

      压缩检查发生在三处：新 prompt 发出前；多轮 run 里每个 turn 的工具结果写入之后、下一次模型请求之前（prepareNextTurn）；以及 provider 报上下文溢出时，压缩后重试一次。压缩 entry 还存了一份当时完整的 system prompt 和工具声明，压缩之后的上下文以它开头。

      扩展从哪些 hook 接入

      到这里可以把前面几节串起来：agent-core 的每个 hook 都由 AgentSession 填入实现，AgentSession 再把其中一部分转发成扩展事件。下表是主路径上最重要的几处。

      agent-core 的口子AgentSession 在里面做什么扩展能收到的事件
      subscribe（事件订阅）message_end 时调用 sessionManager.appendMessage 存盘；维护排队消息的 UI 状态message_*、turn_*、agent_*、tool_execution_* 等全部生命周期事件
      prepareRequest从会话树重建上下文；virtual model 路由；超阈值先压缩压缩时的 session_before_compact、session_compact
      transformContext / onPayload由 core/sdk.ts 在创建 Agent 时注入：发请求前把 messages 和最终的 HTTP 请求体交给扩展改写context、before_provider_request
      prepareNextTurnturn 之间检查压缩；刷新 system prompt 与工具声明同上（压缩时）
      beforeToolCall转发给扩展；扩展返回 { block: true } 就拦下tool_call
      afterToolCall转发给扩展，之后按模型的输入限制缩放结果里的图片tool_result
      finishTurn分发 turn 结束边界；扩展可以要求再跑一个 turnturn_end

      拦截工具：permission-gate.ts

      permission-gate 全文约 25 行：一个 tool_call 处理器就是一道权限闸门 
      export default function (pi: ExtensionAPI) {
  const dangerousPatterns = [/\brm\s+(-rf?|--recursive)/i, /\bsudo\b/i, /\b(chmod|chown)\b.*777/i];
  pi.on("tool_call", async (event, ctx) => {
    if (event.toolName !== "bash") return undefined;
    const command = event.input.command as string;
    if (dangerousPatterns.some((p) => p.test(command))) {
      if (!ctx.hasUI) return { block: true, reason: "Dangerous command blocked (no UI for confirmation)" };
      const choice = await ctx.ui.select(`Dangerous command: ${command}  Allow?`, ["Yes", "No"]);
      if (choice !== "Yes") return { block: true, reason: "Blocked by user" };
    }
    return undefined;
  });
}

      被拦下的调用在第 ④ 步变成一条 isError 结果，reason 作为内容返回给模型，模型据此换一种做法。

      代码里能看到的设计取舍

      下面每条都能在源码注释或代码结构里找到依据；注释里没写原因的，这里也不替作者补。

      工具失败转成错误结果，不往外抛

      选择：找不到工具、校验失败、被拦截、执行抛异常，统统变成 isError: true 的 toolResult。换来：模型能看到错误并自己修正，一次 run 不会因为一个坏参数整体失败。代价：真正的程序 bug 也会被包成「工具报错」交给模型，排查时要看事件流。

      agent-loop.ts:708 prepareToolCall / :821 executePreparedToolCall

      输出被 length 截断时，工具一律不执行

      注释原因：流式工具参数在结束时用「尽力修复」的 JSON 解析器收尾，截断的消息可能产出能解析、能通过校验、但内容不完整的参数。所以宁可全部判失败，提示模型重新发完整参数。

      agent-loop.ts:268 failToolCallsFromTruncatedMessage

      默认并行，但同一文件的写入排队

      并行让多个 read/grep 同时跑；代价是两个 edit 同时改一个文件会互相覆盖（都读到旧内容、各自写回）。withFileMutationQueue 只对同一 realpath 串行，补上这个洞而不牺牲整体并行。

      core/tools/file-mutation-queue.ts

      每个 await 之后检查 abort，而不是在 abort 监听器里 reject

      注释原因：在监听器里直接 reject 会在文件系统操作还没完成时就释放写队列，下一个写入可能和这次未完成的写入交错。逐个检查 signal.aborted 能保证队列锁到当前操作真正结束。

      core/tools/edit.ts:164

      上下文以会话树为准，每次请求重建

      分支、压缩、上下文编辑都是「追加一条 entry」，原始历史不改，回到任何节点都能还原当时的上下文。代价是每次请求都要遍历分支、重算投影；文档没有给出这部分的性能数据。

      agent-session.ts _installAgentRequestProjection

      没有对话就不建文件

      只设置了模型、thinking 级别、system prompt 时不落盘，打开 pi 又关掉不会留下空会话。但从第一条 user 消息开始就落盘，而不是等第一条回复，避免首个 turn 失败时连 prompt 都丢了（issue #10000）。

      什么时候别直接用 pi

      README 明确写了：pi 没有内置的权限系统，不限制文件系统、进程、网络和凭据访问，默认以启动它的用户和进程的权限运行。扩展也在同一个进程里执行，同样拥有全部权限。这带来几个直接的结论：

      • 需要隔离时，要把 pi 放进边界里，而不是指望 pi 自己设限。docs/containerization.md 给了三种做法：Gondolin 扩展（pi 和凭据留在主机，内置工具和 ! 命令转进本地 Linux micro-VM，用的正是前面说的可替换 Operations 接口）、整个 pi 跑在 Docker 里、或跑在有策略控制的 OpenShell 沙箱里。
      • permission-gate 这类扩展是提醒，不是安全边界。它只看 bash 命令的字符串模式，换个写法就能绕过；而且装了来路不明的扩展，等于把整个进程交了出去。
      • 想要开箱即用的 sub-agent、plan mode、审批流程，pi 默认不提供，需要自己写扩展或安装 Pi package。pi 的取舍是保持核心小，把这些留给用户定制。
