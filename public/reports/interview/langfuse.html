Langfuse：LLM 应用的观测、Prompt 与评测

agent 上线后最常见的问题是“它为什么这么回答”“这一单花了多少钱”“改了 prompt 之后变好还是变坏”。Langfuse 是回答这些问题的开源平台：用 trace 记录每次请求里的模型调用、工具调用和检索，用 prompt 管理做版本和发布，用 score、LLM 裁判和数据集实验做评测。本文讲它的数据模型、基于 OpenTelemetry 的 SDK、服务端架构和 2026 年的 v4 改版，两个实验分别对着真实的 langfuse 5.2.0 Python SDK 跑过，采样判定和缓存行为都和真库一致。

先给结论

30 秒背诵版

Langfuse 是柏林团队 2023 年开源的 LLM 工程平台（YC W23），核心是三件事：观测（tracing、成本、延迟、会话）、Prompt 管理（版本、label、客户端缓存）、评测（score、LLM 裁判、人工标注、数据集实验）。代码 MIT 协议，可以自部署，2025 年 6 月把 LLM 裁判、标注队列、playground 也全部开源，只有 SCIM、审计日志这类企业功能收费。2026 年 1 月被 ClickHouse 收购，开源协议不变。

数据模型：一次请求是一个 trace，里面嵌套多个 observation（span、generation、event，以及 agent、tool、retriever 等共 10 种）；多轮对话用 session_id 串成 session；评测结果是挂在 trace、observation 或 session 上的 score。2026 年的 v4 改成“observation 优先”：user_id、session_id 这类 trace 属性直接写进每个 observation，服务端只存一张不可变的宽表，大项目的看板快了 10 倍以上。

SDK 从 2025 年起建立在 OpenTelemetry 上：@observe 装饰器或上下文管理器生成 span，propagate_attributes 给整棵子树带上用户和会话，后台批量异步上报，不阻塞业务；短命进程退出前要 flush()。采样是按 trace id 的确定性采样，同一个 trace 在所有服务里结论一致。服务端是 Web、Worker 两个容器加 Postgres、ClickHouse、Redis、S3：先把原始事件写进 S3，队列里只放引用，Worker 再写进 ClickHouse。截至 2026 年 11 月，最新是 Python SDK 5.2.0，Langfuse Cloud 11 月 16 日起只跑 v4。

定位

Langfuse 解决什么问题

传统 APM（Datadog、Jaeger）擅长记录“哪个接口慢”，但 LLM 应用要看的东西不一样：每次模型调用的完整输入输出、用的哪个 prompt 版本、多少 token、多少钱、模型调了哪些工具、回答质量好不好。这些需要专门的数据模型和界面，这就是 LLM observability 平台的位置。Langfuse 把观测、prompt 和评测放在一个平台里，因为三者是一个闭环：线上 trace 暴露问题，改 prompt，用数据集验证，再发布，再观察。

核心概念

数据模型：trace、observation、session、score

具体例子：用户 u-1024 的两次客服对话

场景是一个电商客服 agent。用户 u-1024 周一打开聊天窗口 chat-42，连发三条消息；周三又新开一个窗口 chat-57 问发票。后端每收到一条消息就处理一次请求、跑一遍 agent。埋点代码只有一处：

@observe(as_type="agent", name="support-agent")      # 每次调用 = 一个新的根 observation = 一个新 trace
def on_message(user_id: str, chat_id: str, text: str) -> str:
    with propagate_attributes(user_id=user_id, session_id=chat_id):   # 聊天窗口 id 当 session_id
        history = load_history(chat_id)        # 对话历史由应用自己存，不是 Langfuse 存
        reply = run_agent(history + [text])    # 内部的模型、工具调用成为子 observation
        save_history(chat_id, text, reply)
        return reply

on_message("u-1024", "chat-42", "我的订单到哪了")   # 周一 10:02
on_message("u-1024", "chat-42", "能退货吗")         # 周一 10:03
on_message("u-1024", "chat-42", "好的谢谢")         # 周一 10:04
on_message("u-1024", "chat-57", "能开发票吗")       # 周三 15:20

四次调用产生四个 trace，各有各的 trace id；它们里面的每个 observation（包括根 support-agent）都带着 user.id = u-1024，前三个 trace 带 session.id = chat-42，第四个带 chat-57。下面的 trace id 前缀就是用 langfuse 5.2.0 跑这段代码、用内存导出器截下来的。

边界怎么划 推荐

一条用户消息（一次请求、一次 agent 运行）是一个 trace，一个聊天窗口是一个 session。用 LangGraph 时，直接把 thread_id 当 session_id。一轮里异步触发的后台任务（比如对话结束后生成摘要）可以是单独的 trace，带上同一个 session_id 也会出现在这个会话里。

对话历史不在 Langfuse 里 注意

第 3 轮 answer 的输入里有前两轮的消息，是应用自己（数据库或 LangGraph checkpointer）读出来拼进去的，Langfuse 只是如实记录。所以越往后的轮次 input token 越多、成本越高，在 session 视图里能直接看出来，这也是需要裁剪或总结历史的信号。

比如把请求 id 当 session_id。每个 session 只有一轮，会话视图看不到上下文，也没法统计“几轮解决问题”“哪一轮开始用户不满意”这类对话级指标。

Trace

一次请求或一次 agent 运行。v4 之后它更像一个分组键：所有 trace_id 相同的 observation 属于同一个 trace。ID 沿用 W3C Trace Context：trace id 是 32 位十六进制，span id 是 16 位。

Observation

trace 里的一步，可以嵌套。最基本的三类：span（有起止时间的一段工作）、generation（模型调用，带 model、参数、usage、cost、prompt）、event（瞬时事件）。

Session

用 session_id 把多轮对话的 trace 串起来，界面上按对话回放。v4 的会话视图把多个 trace 里的用户和助手消息连成一段对话。

User / Environment / Tags

user_id 用来按用户统计成本和反馈；environment 区分 production、staging；tags 和 metadata 用于筛选。

Score

评测结果，四种数据类型：NUMERIC、CATEGORICAL、BOOLEAN、TEXT。来源可以是 SDK/API、界面人工标注、LLM 裁判。可以用 score config 约束取值范围。

Level / Status

observation 有 DEBUG、DEFAULT、WARNING、ERROR 四个级别，配合 status_message 标记失败的步骤，方便筛出出错的调用。

10 种 observation 类型

as_type含义典型例子
span通用的一段工作，默认类型预处理、后处理、业务函数
generation模型调用，可以带 model、usage、cost、promptchat completion
embedding向量化调用，也可以带 usage 和 cost把查询转成向量
agent由 LLM 决定流程、会调工具的部分agent 主循环
tool一次工具或 API 调用查订单、跑 SQL
retriever只读的检索向量库、数据库查询
chain把几个步骤连起来的环节检索结果交给模型
evaluator评估模型输出的步骤自检、打分
guardrail安全防护越狱检测、敏感信息过滤
event没有时长的事件用户点击、缓存命中

类型主要影响界面上的展示和筛选；成本只对 generation 和 embedding 计算。类型用得准，后面配置 LLM 裁判时才能精确地“只评所有 retriever”或“只评根 observation”。

v4：从 trace 表到 observation 宽表

v3 的做法 慢

trace 和 observation 分两张表，SDK 会对同一个 trace 发多次更新（先创建，再补 user_id、输出）。查询时 ClickHouse 要把两张表 join 起来，再对多次更新去重，项目越大越慢。

v4 的做法 快

SDK（Python 4.7.0+、JS 5.4.0+）在上报前就把 user_id、session_id 等 trace 属性写进每个 observation；每个 observation 完成后只写一次，存进一张只追加、不修改的宽表。查询不用 join 也不用去重，大项目的看板快了至少 10 倍，表格首屏从秒级降到毫秒级。

v4 带来的使用习惯变化：trace 级的 update_trace() 被拆掉，改用 propagate_attributes()；LLM 裁判推荐挂在 observation 上，trace 级评测器在 Cloud 上 2026 年 11 月 16 日后停止产出结果。想评“整次请求”，就给根 observation 写好输入输出，用 “Is Root Observation” 过滤器去评它。

接入

SDK：基于 OpenTelemetry 的埋点

Python SDK v3（2025.06）和 JS/TS SDK v4（2025.08）起，Langfuse 的 SDK 就是一层 OpenTelemetry 封装：每个 observation 是一个 OTel span，通过 OTLP/HTTP 发到 /api/public/otel/v1/traces。好处是上下文传播、异步线程、跨服务调用都交给 OTel，别的框架只要输出 OTel span（尤其是带 gen_ai.* 语义约定属性的），也能直接进 Langfuse。

# langfuse 5.x，环境变量 LANGFUSE_PUBLIC_KEY / LANGFUSE_SECRET_KEY / LANGFUSE_BASE_URL
from langfuse import get_client, observe, propagate_attributes

langfuse = get_client()

@observe(as_type="tool")
def get_order(order_id: str) -> dict:
    return db.query(order_id)              # 入参和返回值自动记为 input / output

@observe(as_type="agent", name="support-agent")
def handle(user_id: str, chat_id: str, question: str) -> str:
    with propagate_attributes(user_id=user_id, session_id=chat_id, tags=["support"]):
        prompt = langfuse.get_prompt("support-system")     # 默认取 label=production
        with langfuse.start_as_current_observation(
            name="answer", as_type="generation", model="gpt-5.4-mini", prompt=prompt,
        ) as gen:
            resp = llm(prompt.compile(question=question))
            gen.update(output=resp.text,
                       usage_details={"input": resp.in_tok, "output": resp.out_tok})
        langfuse.score_current_trace(name="answered", value=1, data_type="BOOLEAN")
        return resp.text

几个必须知道的行为

异步批量上报

SDK 用 OTel 的 BatchSpanProcessor：span 结束后进内存队列，后台线程攒够 flush_at（默认 512 个）或每隔 flush_interval（默认 5 秒）发一批，默认 gzip 压缩。业务线程不等网络，Langfuse 挂了也不影响主流程，代价是进程被直接杀掉时队列里的数据会丢。

flush() 与 shutdown()

长期运行的服务不用管，退出时 SDK 会注册清理。Lambda、云函数、一次性脚本、Celery 任务执行完就冻结或退出，后台线程来不及发，必须在返回前调 flush()。这是“本地有数据、线上看不到 trace”最常见的原因。

propagate_attributes

在上下文里设置 user_id、session_id、tags、metadata、version、trace_name，之后创建的所有子 observation 都会带上。要在第一个子 observation 创建之前设置，否则之前创建的 observation 没有这些字段。as_baggage=True 时还会通过 W3C baggage 传到下游服务。值有限制：字符串，最长 200 字符，metadata 的值也会转成字符串。

默认 span 过滤

v4 起 SDK 默认只导出三类 span：Langfuse 自己创建的、带 gen_ai.* 属性的、来自已知 LLM 插桩库的。数据库、HTTP 客户端这类通用 span 不再进 Langfuse，trace 更干净。想全收就传 should_export_span=lambda s: True；注意过滤掉父 span 会让子 span 变成“孤儿”。

脱敏

mask 函数在上报前处理 input、output、metadata；mask_otel_spans 能处理包括第三方插桩在内的原始 OTel span。函数是同步的，要写得快，否则会拖慢导出队列。也可以在 @observe 上用 capture_input=False 干脆不记录。

和已有 OTel 共存

如果进程里已经注册了全局 TracerProvider，Langfuse 会复用它，此时 Langfuse 的 span 也可能被发到你的其他后端，反之亦然。想隔离就给 Langfuse 传一个独立的 tracer_provider。下一节会看到，这时 sample_rate 还会失效。

版本对应：Python SDK v3 用 start_as_current_span、start_as_current_generation；v4 统一成 start_as_current_observation(as_type=...)，update_current_trace() 拆成 propagate_attributes() 等；v5（要求 Python 3.11+、服务端 v4.59.0+）删掉了 api.legacy.* 和 trace 级 input/output 的设置方法。面试时写 v4/v5 的写法更稳妥。

原理

采样与 trace id：为什么能跨服务保持一致

流量大时没必要全量记录，sample_rate（或环境变量 LANGFUSE_SAMPLE_RATE）设置采样比例，默认 1.0。采样以 trace 为单位：一个 trace 要么整个保留，要么整个丢掉，不会出现半棵树；被丢掉的 trace 上的 score 也不会上报。

Python SDK 的实现是给 OTel 的 TracerProvider 装一个 TraceIdRatioBased 采样器，它不掷骰子，而是看 trace id 的低 64 位：

采样  ⟺  (trace_id mod 264)  <  round⁡ ⁣(r⋅264)\text{采样} \iff \big(\text{trace\_id} \bmod 2^{64}\big) \;<\; \operatorname{round}\!\big(r \cdot 2^{64}\big)采样⟺(trace_idmod264)<round(r⋅264)

随机生成的 trace id 低 64 位均匀分布，所以长期来看采样比例就是 rrr。关键在于这是 trace id 的确定性函数：

  • 同一个 trace 经过多个服务，只要每个服务用相同的 rrr，结论就相同，不需要互相通知。
  • 采样率小的集合是采样率大的集合的子集：r=0.1r=0.1r=0.1 时保留的 trace，在 r=0.5r=0.5r=0.5 时一定也保留。所以上游 0.1、下游 0.5 时，上游保留的 trace 下游一定完整。
  • 用 Langfuse.create_trace_id(seed="order-1001") 可以从业务 id 生成 trace id（取 SHA-256 的前 16 字节），同一个订单号永远对应同一个 trace id，方便事后查找、补打 score，也意味着“某个订单号会不会被采样”是固定的。

一个真库里验证过的坑：sample_rate 只在 Langfuse 自己创建 TracerProvider 时生效。如果进程里已经有别的库注册了全局 provider，Langfuse 会直接复用它，sample_rate=0.01 被静默忽略，实测 200 个 trace 全部被记录。这时要在你自己的 provider 上配采样器，或者给 Langfuse 传独立的 tracer_provider。

ClickHouseobservation、score 等观测数据列存 OLAP，写入量大、按时间范围聚合快；v2 全部存在 Postgres，v3 为了支撑上亿条记录的摄取迁了过来
Redis / Valkey摄取队列、API key 和 prompt 的服务端缓存低延迟；prompt 接口先查 Redis，没有再查 Postgres
S3 / Blob原始事件、图片音频等多模态附件、大批量导出便宜、耐久，作为摄取的缓冲和事实来源

自部署：Docker Compose 只适合本地和测试（单机、无高可用）；生产用 Kubernetes Helm chart 或 AWS、Azure、GCP 的 Terraform 模板，ClickHouse、Postgres、Redis、S3 都可以换成云托管服务。自部署 v3 升级到 v4 有 legacy 和 dual 写入模式，可以分步迁移；用 Helm 自带 ClickHouse 的要先把 chart 从 v1 升到 v2。

Prompt 管理

版本、label 与客户端缓存

prompt 写死在代码里，每次改措辞都要发版，也说不清线上用的是哪一版。Langfuse 把 prompt 存在平台上：每次保存生成一个新的版本号（1、2、3…，不可变），再用 label 指向某个版本。production 是默认 label，latest 自动指向最新版本，也可以自定义 staging、tenant-a 等。发布就是把 production 移到新版本，回滚就是移回去，代码不用动。

prompt = langfuse.get_prompt("support-system")                    # label=production
prompt = langfuse.get_prompt("support-system", label="staging")
prompt = langfuse.get_prompt("support-system", version=7)         # 固定版本
prompt = langfuse.get_prompt("support-system", cache_ttl_seconds=0, label="latest")  # 开发环境

text = prompt.compile(question="能退货吗")       # 填 {{question}} 变量
cfg = prompt.config                             # 模型、温度等也可以跟着 prompt 版本走

# 把 prompt 挂到 generation 上，平台就能按 prompt 版本统计延迟、成本和 score
with langfuse.start_as_current_observation(name="answer", as_type="generation", prompt=prompt): ...

prompt 分 text 和 chat 两种；可以用 @@@langfusePrompt:name=xxx|label=production@@@ 引用别的 prompt 做组合。最有价值的是“链接到 generation”：配合 A/B 两个 label 各给一部分流量，就能直接对比两个版本的线上质量分和成本。

客户端缓存：stale-while-revalidate

如果每次请求都去拉 prompt，Langfuse 就成了业务的单点和延迟来源。SDK 在进程内缓存 prompt，默认 TTL 60 秒（环境变量 LANGFUSE_PROMPT_CACHE_DEFAULT_TTL_SECONDS 可改），规则读源码可以概括成三条：

缓存状态行为是否阻塞
没有缓存（进程刚启动）同步请求 API；失败时有 fallback 就返回 fallback（is_fallback=True），否则抛异常阻塞
未过期直接返回缓存不阻塞
已过期立刻返回旧值，同时把刷新任务放进后台线程；同一个 key 同时只有一个刷新任务；刷新失败就继续用旧值，下次请求再试不阻塞
cache_ttl_seconds=0每次都同步请求 API阻塞

过期判断用的是整数秒：缓存写入时记下 ⌊t写入⌋+TTL\lfloor t_{\text{写入}} \rfloor + \text{TTL}⌊t写入​⌋+TTL，当 ⌊t⌋\lfloor t \rfloor⌊t⌋ 大于它时才算过期，所以实际新鲜期在 TTL 到 TTL+1 秒之间。这套设计的结论是：发布新版本后，线上最多要过“TTL + 一次拉取耗时 + 下一次请求到来”这么久才会用上，而且第一个看到过期的请求拿到的仍是旧版本。要立即生效可以调 clear_prompt_cache()，或者在启动时预热。服务端那边，prompt 接口先查 Redis 再查 Postgres；如果服务端返回 404（prompt 被删），SDK 会把缓存清掉。

成本

token 与成本怎么算

成本只记在 generation 和 embedding 上，父节点和 trace 的成本是子节点汇总。每个 generation 有两组数：usage_details（各类 token 的数量）和 cost_details（各类的美元金额）。

cost  =  ∑k∈usage 类别uk⋅pk,k∈{input, output, cache_read_input_tokens, … }\text{cost} \;=\; \sum_{k \in \text{usage 类别}} u_k \cdot p_k ,\qquad k \in \{\texttt{input},\ \texttt{output},\ \texttt{cache\_read\_input\_tokens},\ \dots\}cost=k∈usage 类别∑​uk​⋅pk​,k∈{input, output, cache_read_input_tokens, …}

上报的 vs 推算的

成本可以直接上报（比如供应商返回了费用，或者有自己的协议价），也可以由 Langfuse 推算：用 generation 的 model 字段去匹配模型定义，拿到单价乘以 usage。两者都有时以上报的为准。只上报 usage 不上报成本是最常见的用法。

模型定义

每个模型定义有一个正则 match_pattern，例如 (?i)^(gpt-4o)$，和每类 token 的单价。Langfuse 内置 OpenAI、Anthropic、Google 的定价，自定义的定义优先级更高。自托管模型、协议价都靠自定义模型定义。

usage 的类别要互斥

每个 token 只能算一次。OpenAI 返回的 prompt_tokens 包含缓存命中的部分，Langfuse 识别 OpenAI 格式时会把 cached_tokens 从 input 里减掉，单独记为缓存读取，分别按不同单价计费。自己拼 usage 时如果重复计算，成本会偏高。

分档定价与不追溯

一个模型可以有多个价格档，比如输入超过 200k token 走长上下文价。按优先级检查条件，第一个满足的生效，都不满足用默认档。成本在摄取时算好存下来，之后改价格只影响新数据，旧的 generation 不会重算。

Langfuse 已经不再用 tokenizer 根据输入输出估算 token 数。既没有上报 usage 也没有上报成本的 generation，成本就是空的。所以接入自定义模型时，一定要把供应商返回的 usage 填进去。

from langfuse import get_client, Evaluation

langfuse = get_client()
dataset = langfuse.get_dataset("support-regression")

def task(*, item, **kwargs):
    return support_agent(item.input["question"])

def exact(*, input, output, expected_output, **kwargs):
    return Evaluation(name="exact_match", value=float(output == expected_output))

def avg(*, item_results, **kwargs):
    vals = [e.value for r in item_results for e in r.evaluations if e.name == "exact_match"]
    return Evaluation(name="avg_exact_match", value=sum(vals) / len(vals))

result = dataset.run_experiment(name="prompt-v8", task=task,
                                evaluators=[exact], run_evaluators=[avg])
print(result.format())

LLM 裁判的成本要算清楚：每条被评的 observation 都是一次额外的模型调用，官方估计每次 0.01 到 0.1 美元。线上评测几乎都要配采样和过滤，只评关键步骤，简单的检查交给代码评测器。裁判本身的偏差（位置、长度、自我偏好）和缓解方法见本站《大模型评测》一文。

自测

高频追问

Langfuse 是什么？和传统 APM 有什么区别？

开源的 LLM 工程平台，做观测、prompt 管理和评测。传统 APM 关心接口延迟和错误率，LLM 应用还要看完整的输入输出、prompt 版本、token 和成本、agent 每一步的决策、回答质量，这些需要专门的数据模型（generation、score、session）和界面。

trace、observation、session、score 分别是什么？

trace 是一次请求，observation 是其中的一步（span、generation、event 等 10 种，可以嵌套），session 用 session_id 把多轮对话的 trace 串起来，score 是评测结果（数值、类别、布尔、文本），可以挂在 trace、observation、session 或数据集实验上。

多轮对话里，trace 和 session 怎么划分？

一条用户消息对应一次请求、一次 agent 运行，是一个 trace；一个聊天窗口是一个 session，用 propagate_attributes(session_id=chat_id) 让这一轮的所有 observation 带上它。例如用户在 chat-42 里发 3 条消息，就是 3 个 trace、1 个 session；换个窗口再问，就是新 session。session 不需要创建，只是相同 session_id 的分组。不要把整段对话塞进一个 trace（根节点迟迟不结束、每轮指标混在一起），也不要每条消息一个 session（看不到上下文）。用 LangGraph 时 thread_id 直接当 session_id。

span 和 generation 有什么区别？

generation 是专门表示模型调用的 observation，多了 model、model_parameters、usage_details、cost_details、prompt、completion_start_time（用来算首 token 延迟）等字段，成本只在 generation 和 embedding 上计算。span 是通用的一段工作。

Langfuse 的 SDK 为什么要基于 OpenTelemetry？

上下文传播（嵌套、异步、线程、跨服务）是 OTel 已经解决好的问题；任何输出 OTel span 的框架都能接入，不用每个框架写一个集成；还能和公司已有的 OTel 体系共存。代价是要理解 TracerProvider、span 过滤这些 OTel 概念，比如已注册全局 provider 时 sample_rate 会失效。

埋点会不会拖慢业务？Langfuse 挂了怎么办？

不会阻塞：span 结束后进内存队列，后台线程按 512 个一批或每 5 秒批量发送，gzip 压缩。Langfuse 不可用时导出失败、重试，最终丢弃，业务不受影响。prompt 拉取有缓存，过期也先返回旧值。真正会阻塞的只有冷启动时第一次拉 prompt，可以用 fallback 兜底。

为什么线上看不到 trace？

最常见是短命进程（Lambda、脚本、Celery 任务）退出前没 flush()；其次是 v4 默认 span 过滤把非 LLM 的 span 丢了、父 span 被过滤导致树断开；还有采样率、密钥和区域地址配错、环境不对。排查时开 debug=True 能看到被丢掉的 span。

采样是怎么做的？多个服务会不会采样结论不一致？

按 trace 采样，用 OTel 的 TraceIdRatioBased：trace id 低 64 位小于 round⁡(r⋅264)\operatorname{round}(r\cdot 2^{64})round(r⋅264) 就保留。它是 trace id 的确定性函数，各服务采样率相同时结论一定相同；采样率小的保留集合是采样率大的子集。被丢掉的 trace 上的 score 也不上报。

怎么把业务的订单号和 trace 对应起来？

用 create_trace_id(seed=订单号) 生成确定性的 trace id（SHA-256 前 16 字节），创建 observation 时传 trace_context={"trace_id": ...}。之后用订单号就能算出 trace id，异步补打 score（比如用户第二天退货）也能挂到原来的 trace 上。

propagate_attributes 是做什么的？和 v3 的 update_current_trace 有什么区别？

它在上下文里设置 user_id、session_id、tags、metadata 等，之后创建的每个 observation 都会带上这些字段。v3 是事后更新 trace 记录，服务端要合并多次更新；v4 改成每个 observation 自带，服务端不用 join 和去重。要在创建子 observation 之前调用，值是不超过 200 字符的字符串。

Langfuse 自部署需要哪些组件？为什么要 ClickHouse？

Web 和 Worker 两个容器，加 Postgres（事务数据）、ClickHouse（观测数据）、Redis（队列和缓存）、S3（原始事件和附件）。观测数据写入量大、按时间聚合查询多，是典型的 OLAP 场景，v2 全部存在 Postgres，v3 为了支撑上亿条记录换成了列存的 ClickHouse。

摄取为什么先写 S3 再进队列？

削峰和容错。Web 收到事件写进 S3 后只往 Redis 放引用就返回，不等数据库；Worker 按自己的速度消费。流量突增时不会因为数据库写不过来而超时，ClickHouse 短暂故障时事件也还在 S3 里，恢复后重新处理即可。队列里只放引用，也避免 Redis 被大 payload 撑爆。

v4 改了什么？为什么快？

从 trace 表加 observation 表改成一张 observation 宽表：SDK 把 trace 属性写进每个 observation，每个 observation 只写一次、不可修改。v3 查询时要 join 两张表并对多次更新去重，v4 不需要，大项目的看板快了 10 倍以上，也为物化视图等优化打了基础。

prompt 管理的 version 和 label 有什么区别？怎么回滚？

version 是每次保存自动递增、不可变的版本号；label 是可移动的指针，production 是默认，latest 自动指向最新。代码里按 label 取，发布和回滚都是移动 label，不用改代码、不用发版。需要绝对稳定时可以按 version 固定。

prompt 缓存是怎么工作的？发布新版本多久生效？

进程内缓存，默认 TTL 60 秒，stale-while-revalidate：没缓存时同步拉；未过期直接返回；过期后先返回旧值，后台单线程刷新，同一个 key 只刷一次。所以新版本要等缓存过期、下一次请求触发刷新、刷新完成之后才生效，第一个看到过期的请求拿到的还是旧版本。要立即生效可以 clear_prompt_cache()。

成本是怎么算的？为什么我的成本是空的或者不对？

有上报的成本就用上报的；否则用 model 去正则匹配模型定义，按单价乘以各类 usage。成本空：没上报 usage，或者模型名匹配不上任何定义（Langfuse 已不再自己估算 token）。成本偏高：usage 类别重复计算了缓存 token。改价格不会追溯历史数据。

线上怎么做自动评测？要注意什么？

配 LLM 裁判评测器，目标选 observation（v4 推荐）或实验，用过滤条件和采样比例控制范围，把输入输出映射到 prompt 变量，输出分数和理由。注意成本（每次是一次模型调用）、裁判本身的偏差（要用人工标注队列校准一致率），简单的规则检查用代码评测器。

数据集实验怎么接进 CI？

维护一个回归数据集（多来自线上坏例），PR 里用 run_experiment 让新版本跑一遍，evaluators 逐条打分、run_evaluators 算汇总，分数低于阈值就抛 RegressionError 让 CI 失败；官方提供 langfuse/experiment-action。实验结果和每条 trace 链接，在对比视图里看新旧版本的差异。

怎么处理敏感数据？

上报前用 mask 或 mask_otel_spans 脱敏，或在 @observe 上关闭 capture_input、capture_output；数据不能出境就自部署或选对应区域（Cloud 有 EU、US、JP、HIPAA 区域）；配数据保留策略；API key 按最小权限划分。

Langfuse 和 LangSmith 怎么选？

Langfuse 开源可自部署、与框架无关、基于 OTel；LangSmith 是商业产品，和 LangChain、LangGraph 集成最深，并提供托管部署。数据要留在内网、技术栈混杂、在意成本选 Langfuse；全家桶用 LangChain 并需要托管部署可以选 LangSmith。Langfuse 也能通过 CallbackHandler 追踪 LangGraph。

2 分钟口述

答题模板

  1. 先讲定位。开源的 LLM 工程平台，观测、prompt 管理、评测三件事形成闭环；MIT 协议可自部署，2026 年被 ClickHouse 收购。
  2. 讲数据模型。trace 里嵌套 observation（generation 带 model、usage、cost、prompt），session 串多轮，score 是评测结果；v4 改成 observation 优先的不可变宽表，trace 属性由 SDK 写进每一行。
  3. 讲 SDK。基于 OpenTelemetry，@observe 和上下文管理器埋点，propagate_attributes 传用户和会话；后台批量异步上报，短命进程要 flush()；按 trace id 确定性采样，跨服务一致。
  4. 讲架构。Web、Worker 加 Postgres、ClickHouse、Redis、S3；先写 S3 再放队列引用，Worker 异步写 ClickHouse，用来削峰和容错。
  5. 讲 prompt 和评测。version 不可变、label 可移动，发布和回滚都是移 label；客户端缓存 stale-while-revalidate；成本按 usage 乘单价、摄取时算定；在线用 LLM 裁判和代码评测器，离线用数据集实验接 CI。

常见失分点：说 SDK 每次调用都同步上报（是后台批量）；说采样是随机掷骰子（是 trace id 的确定性函数）；以为设了 sample_rate 就一定生效（已有全局 TracerProvider 时被忽略）；说改了 prompt 立刻生效（要等缓存过期并刷新）；说 Langfuse 会自己估算 token（已经不估了）；说改模型价格会重算历史成本（不追溯）；还在用 v3 的 start_as_current_span 和 update_current_trace。
