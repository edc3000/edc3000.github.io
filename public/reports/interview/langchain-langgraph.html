LangChain 与 LangGraph

LangChain 和 LangGraph 出自同一家公司，现在是上下两层：LangGraph 是底层的编排运行时，把 agent 写成一张带状态的图，负责并行、存档、暂停和恢复；LangChain 1.0 收缩成 create_agent 加中间件，编译出来就是一张 LangGraph 图。本文先讲两者的关系和演进，再讲 LangGraph 的状态、reducer、super-step 执行模型、checkpoint、interrupt，最后讲多智能体和 2026 年的新变化。两个实验分别对着真实的 langgraph 1.2.20 跑过，checkpoint 的编号和报错都和真库一致。

先给结论

30 秒背诵版

LangChain 是 Harrison Chase 2022 年 10 月开源的 LLM 应用框架，早期提供提示词模板、链（chain）、各家模型和向量库的统一接口；2023 年推出 LCEL，所有组件实现同一个 Runnable 接口，用 | 拼成流水线。它被诟病的地方是抽象层太厚、版本变化快，老的 AgentExecutor 是个黑盒循环，难以插入自定义逻辑。

LangGraph 2024 年 1 月发布，把 agent 写成一张状态图：State 是共享状态，每个字段可以配 reducer 决定怎么合并；Node 是读状态、返回更新的函数；Edge 决定下一步，条件边可以分支和成环。运行时借鉴 Pregel，按 super-step 执行：同一步的节点并行跑，写入在步末统一合并。配上 checkpointer，每个 super-step 存一次档，于是有了多轮记忆、interrupt() 人工审批、时间旅行和失败后从断点恢复。

2025 年 10 月两者同时发布 1.0。LangChain 1.0 只保留 create_agent、中间件、模型和工具接口，底层就是编译出来的 LangGraph 图；旧的链和检索器移到 langchain-classic。一句话分工：要标准的“模型调工具”循环用 LangChain，要自己设计流程、分支、并行、长时间运行和人工介入用 LangGraph，两者可以混用。到 2026 年 11 月，最新版是 langchain 1.4.9 和 langgraph 1.2.20。

LangChain 基础

组件、Runnable 与 LCEL

LangChain 最早的价值是统一接口：几十家模型、向量库、文档加载器各有各的 SDK，LangChain 给它们套上同一层抽象，换模型只改一行。到 1.x 这部分仍然是核心，放在 langchain-core 和各个集成包里。

组件作用1.x 里的位置
Chat model统一的 invoke、stream、bind_tools、with_structured_output；init_chat_model("provider:model") 按字符串创建langchain.chat_models
MessagesHumanMessage、AIMessage（带 tool_calls）、ToolMessage（带 tool_call_id）；1.0 加了跨厂商统一的 content_blocks（文本、推理、工具调用、引用等）langchain.messages
Tools@tool 从函数签名和 docstring 生成 JSON Schema；可以注入运行时状态，不暴露给模型langchain.tools
Embeddings、向量库、检索器RAG 的三件套；文本切分器在 langchain-text-splittersembeddings 在 langchain.embeddings，老检索器在 langchain-classic
Prompt 模板、输出解析器LCEL 时代的主角；有了原生工具调用和结构化输出后，用得少了langchain-core

LCEL：所有东西都是 Runnable

每个组件都实现 invoke、batch、stream 及其异步版本。a | b 生成 RunnableSequence，前一个的输出是后一个的输入；字典会被转成 RunnableParallel，并行执行各分支。组合出来的东西还是 Runnable，所以自动获得流式、批量、异步、重试（with_retry）、降级（with_fallbacks）和追踪。

# 经典 RAG 链（LCEL 写法）
chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | model
    | StrOutputParser()
)
chain.invoke("LangGraph 的 checkpoint 存在哪？")

LCEL 适合什么

有向无环的固定流程：检索 → 拼提示词 → 生成 → 解析。每一步做什么在写代码时就确定了，没有“根据模型输出决定下一步”的循环。

LCEL 不适合什么

agent 要循环（调工具、看结果、再决定），要分支、要在中途停下等人确认、要在崩溃后续跑。用 Runnable 硬拼会变成难以调试的嵌套结构，这正是 LangGraph 要解决的问题。

LangChain 1.x

create_agent 编译出来是什么

create_agent 实现的是最常见的 agent 循环：调模型，如果模型要调工具就执行工具，把结果交回模型，直到模型不再调工具。它不是一个黑盒，而是返回一个编译好的 LangGraph 图（CompiledStateGraph），所以 checkpointer、interrupt、流式输出、Studio 可视化全部可以直接用。

from langchain.agents import create_agent
from langchain.agents.middleware import SummarizationMiddleware, HumanInTheLoopMiddleware
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model="anthropic:claude-sonnet-4-6",
    tools=[search, send_email],
    system_prompt="你是客服助手",
    middleware=[
        SummarizationMiddleware(model="openai:gpt-5.4-mini", trigger=("tokens", 80000)),
        HumanInTheLoopMiddleware(interrupt_on={"send_email": True}),
    ],
    checkpointer=InMemorySaver(),
)
agent.invoke({"messages": [{"role": "user", "content": "查一下订单 42"}]},
             {"configurable": {"thread_id": "user-1"}})

循环什么时候结束

  • 最后一条 AIMessage 没有工具调用，这是标准的出口。
  • 本轮执行的工具都设置了 return_direct=True。
  • 用了结构化输出，并且已经生成了 structured_response。
  • 中间件在状态里写了 jump_to="end"。
  • 都不满足时，安全网是 recursion limit：create_agent 默认把它设为 9999 个 super-step，超了抛 GraphRecursionError。实际项目应该用 ModelCallLimitMiddleware、ToolCallLimitMiddleware 设置更小的上限。

结构化输出的三种策略

策略做法特点
ToolStrategy(Schema)把输出格式定义成一个“工具”，模型调用它就等于交答案所有支持工具调用的模型都能用；handle_errors 处理解析失败或一次调用多个的情况，把错误发回模型重试
ProviderStrategy(Schema)用厂商原生的结构化输出（约束解码）格式由厂商保证；1.2 起支持严格模式，只有部分模型支持
直接传类型按模型 profile 自动选：支持原生结构化输出就用 Provider，否则用 Tool默认推荐

和 0.x 的区别：以前要先跑完 agent 再额外调一次模型做格式化，1.0 把结构化输出放进主循环，少一次调用。结果放在返回状态的 structured_response 里。

LangChain 1.x

中间件：六个钩子与执行顺序

中间件是 1.0 最重要的设计。以前要改 agent 行为，只能改提示词，或者把 AgentExecutor 整个重写；现在把可变的部分抽成钩子，继承 AgentMiddleware 重写其中几个，或者用同名装饰器写成函数。

钩子何时运行典型用途
before_agent每次调用开始时一次加载记忆、校验输入
before_model每次调模型前（节点）裁剪、压缩消息历史，检查调用次数
wrap_model_call包住模型调用（不是节点，是函数包装）动态换模型、筛选工具、改系统提示词、重试、降级、缓存
after_model模型返回后（节点）人工审批工具调用、内容审核、写 jump_to 改路由
wrap_tool_call包住每个工具调用工具重试、把异常转成错误消息、权限检查
after_agent结束前一次保存记忆、清理、记录日志

常用内置中间件

中间件作用
SummarizationMiddleware历史超过 token 或消息数阈值时，把旧消息总结成一条，保留最近若干条
HumanInTheLoopMiddleware指定的工具调用前暂停，等人决定：approve、edit、reject、respond（替工具直接回答）
ModelCallLimitMiddleware、ToolCallLimitMiddleware限制每个线程或每次运行的调用次数，防止死循环烧钱
ModelRetryMiddleware、ToolRetryMiddleware、ModelFallbackMiddleware指数退避重试；主模型失败时换备用模型
PIIMiddleware识别邮箱、卡号等敏感信息，脱敏、遮盖或拦截
LLMToolSelectorMiddleware工具很多时先用小模型挑出相关的几个，再交给主模型
ContextEditingMiddleware清理早期的工具结果，给上下文腾地方
TodoListMiddleware、ShellToolMiddleware、FilesystemFileSearchMiddleware给 agent 加待办清单、shell、文件搜索工具

中间件可以声明自己的状态字段（自定义 state_schema），这些字段会合并进图的 State。例如调用计数就存在状态里，有 checkpointer 时跨轮次保留。

LangGraph 核心

StateGraph：State、Node、Edge

LangGraph 的口号是“节点干活，边决定下一步”。写一张图分四步：定义 State，加节点，连边，compile()。

import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send, Command

class State(TypedDict):
    question: str                                   # 没写 reducer：新值覆盖旧值
    docs: Annotated[list[str], operator.add]        # reducer：多个节点的写入拼接
    draft: str
    rounds: int

def planner(s): return {"rounds": 0}
def search_a(s): return {"docs": ["A 的结果"]}
def search_b(s): return {"docs": ["B 的结果"]}
def writer(s):   return {"draft": "..."}
def reviewer(s): return {"rounds": s["rounds"] + 1}

g = StateGraph(State)
for name, fn in [("planner", planner), ("search_a", search_a), ("search_b", search_b),
                 ("writer", writer), ("reviewer", reviewer)]:
    g.add_node(name, fn)
g.add_edge(START, "planner")
g.add_edge("planner", "search_a"); g.add_edge("planner", "search_b")   # 扇出：并行
g.add_edge(["search_a", "search_b"], "writer")                         # 扇入：两个都完成才跑
g.add_edge("writer", "reviewer")
g.add_conditional_edges("reviewer", lambda s: "writer" if s["rounds"] < 3 else END)
graph = g.compile(checkpointer=InMemorySaver())

State 与 reducer

节点不改状态，只返回更新（一个字典）。每个字段是一个通道（channel），默认规则是覆盖；用 Annotated[类型, reducer] 指定合并函数，签名是 r(旧值,更新)→新值r(\text{旧值}, \text{更新}) \to \text{新值}r(旧值,更新)→新值。消息列表用 add_messages：按消息 id 追加或替换，还能用 RemoveMessage 删除。MessagesState 是预置的只含 messages 的状态。

边的几种写法

普通边 add_edge；条件边 add_conditional_edges，路由函数返回节点名、节点名列表（扇出）或 Send 列表；START、END 是虚拟节点。等待多个上游用 add_edge([a, b], c)，否则 c 会在任一上游完成时就被触发。

Send：运行时决定扇出数量

Send("worker", {"item": x}) 让一个节点以自定义输入跑一次。返回 nnn 个 Send 就有 nnn 个并行任务，nnn 在运行时才确定，适合 map-reduce：比如每个子问题一个检索任务，结果用 reducer 汇总。

Command：更新和跳转一起做

节点返回 Command(update={...}, goto="next")，同时改状态和指定下一个节点，不用再写条件边；graph=Command.PARENT 从子图跳到父图的节点，多智能体交接就靠它；Command(resume=...) 作为输入恢复被中断的图。返回类型要标注 Command[Literal[...]]，图才能画出这些边。

其他要点：input_schema、output_schema 可以让图的输入输出只暴露部分字段；context_schema 定义不进状态的运行时上下文（用户 id、数据库连接），节点通过 Runtime 读取；add_node 可以配 RetryPolicy、CachePolicy，1.2 起还能配超时和错误处理。除了图写法，还有 Functional API：@entrypoint 包住一个普通函数，@task 标记可并行、结果会被存档的步骤，适合不想画图的场景，运行时是同一个。

运行时

执行模型：Pregel 风格的 super-step

LangGraph 的运行时叫 Pregel，名字来自 Google 2010 年的大规模图计算系统，思想是 BSP（bulk synchronous parallel，整体同步并行）。图的执行被切成一个个 super-step，每一步分三个阶段：

形式化地写，设第 ttt 步激活的节点集合是 AtA_tAt​，节点 nnn 读快照 StS_tSt​ 返回更新 Δn\Delta_nΔn​，字段 kkk 的 reducer 是 rkr_krk​。对 AtA_tAt​ 中每个写了 kkk 的节点 n1,n2,…n_1,n_2,\dotsn1​,n2​,…，依次合并：

St+1[k]=rk(rk(St[k], Δn1[k]), Δn2[k])⋯S_{t+1}[k] = r_k\big(r_k(S_t[k],\,\Delta_{n_1}[k]),\,\Delta_{n_2}[k]\big)\cdotsSt+1​[k]=rk​(rk​(St​[k],Δn1​​[k]),Δn2​​[k])⋯

没配 reducer 的字段相当于“只能接收一个值”：同一步里两个节点写同一个字段就抛 InvalidUpdateError，因为覆盖顺序无法确定。这是面试最常问的并行坑。

这样设计的好处

  • 确定性：并行节点互不干扰，合并顺序由 reducer 决定，结果可复现。
  • 天然的存档点：每个 super-step 结束时状态一致，正好存 checkpoint。
  • 失败只重跑失败的：同一步里成功节点的写入作为 pending writes 先存下来，恢复时不用重跑。

recursion limit

限制的是一次运行的 super-step 数，不是节点调用次数。超过就抛 GraphRecursionError。默认值在 1.0.6 之前是 25，1.0.6 起改成 10000，1.1.4 起是 10007，可以用环境变量 LANGGRAPH_DEFAULT_RECURSION_LIMIT 改，也可以在 config 顶层传 recursion_limit（不是放在 configurable 里）。老面经里“默认 25”的说法已经过时。

LangGraph 核心

持久化：checkpointer、thread 与 store

编译时传入 checkpointer，每个 super-step 结束后把完整状态存成一个 checkpoint，按 thread_id 分组。同一个 thread_id 再次调用会接着上次的状态跑，这就是多轮对话的“短期记忆”。

概念说明
thread一串 checkpoint 的集合，用 config["configurable"]["thread_id"] 指定，通常对应一个会话
checkpoint某个 super-step 结束时的快照，StateSnapshot 字段有 values、next、config（含 checkpoint_id）、metadata（source、step）、created_at、parent_config、tasks、interrupts
编号输入是 step −1-1−1（source 为 input，next 是 __start__），之后每个 super-step 一个，source 为 loop；update_state 产生的是 update，从旧 checkpoint 重跑产生的是 fork
读写get_state 取最新；get_state_history 列出全部；update_state(config, values, as_node=...) 以某个节点的名义写入，会产生新 checkpoint
实现InMemorySaver（开发用，重启即丢）、SqliteSaver、PostgresSaver，还有 Redis、MongoDB 等社区实现；都有异步版本
durability何时写入存储："sync" 每步写完才进下一步，"async"（默认）下一步执行时异步写，"exit" 只在结束时写（快，但中途崩溃会丢进度）

checkpointer 带来的能力

  • 记忆：同一 thread 多轮对话。
  • 人在环中：interrupt 必须有 checkpointer，暂停时状态存下来，人可以隔几天再回来恢复。
  • 时间旅行：回放、分叉、调试。
  • 容错（durable execution）：进程崩溃后用同一个 thread 继续，已完成的 super-step 不重跑。

Store：跨 thread 的长期记忆

checkpoint 只属于一个 thread。用户偏好这类要跨会话的信息放在 Store（BaseStore）里：按 namespace 元组（比如 ("memories", user_id)）组织键值，put、get、search，配了 embedding 可以做语义检索。编译时传 store=，节点通过 runtime.store 访问。

checkpoint 存的是完整状态，长对话里会越来越大。1.2 引入了 beta 的 DeltaChannel：消息这类只增长的字段每步只存增量，每隔 KKK 步存一次完整快照；生产环境还要定期清理旧 checkpoint。

LangGraph 核心

人在环中：interrupt 与 Command(resume=...)

from langgraph.types import interrupt, Command

def approve(state):
    decision = interrupt({"question": "批准退款吗？", "amount": state["amount"]})
    return {"decision": decision}

graph.invoke({"amount": 300}, config)              # 跑到 interrupt 停下，返回值里有 __interrupt__
graph.invoke(Command(resume="yes"), config)        # 同一个 thread_id，带着人的答复恢复

第一次调用 interrupt() 时抛出一个特殊异常，运行时捕获后把状态存档、把参数交给调用方，图停在这个节点。恢复时 整个节点从头重新执行，执行到 interrupt() 时不再暂停，而是直接返回 resume 的值。这带来三条规则：

  • interrupt 之前不要放有副作用的操作（发通知、扣款、写库），否则恢复时会再执行一次。要么放到 interrupt 之后，要么放到单独的节点，要么保证幂等。
  • 一个节点里有多个 interrupt() 时，按调用顺序和 resume 值一一对应，所以不能把 interrupt 放在顺序会变的条件分支里。
  • 不要用 try/except Exception 包住 interrupt()，否则暂停用的异常被吞掉，图不会停下来。

另一种暂停方式是静态断点：编译时传 interrupt_before=["node"] 或 interrupt_after，主要用于调试。LangChain 的 HumanInTheLoopMiddleware 也是基于 interrupt()：默认的批量模式在 after_model 里把本轮所有需要审批的工具调用合成一次中断；1.4.6 起可以设 interrupt_mode="per_call"，在 wrap_tool_call 里每个工具调用单独中断、单独回答，每个中断带一个 response_schema，答复保存前先校验，官方计划在下一个大版本把它设为默认。

进阶

子图与多智能体

子图：编译好的图本身就是一个 Runnable，可以直接作为父图的节点。父子状态有同名字段时直接共享；字段不同时，在节点函数里手动调用子图并转换输入输出。子图可以有自己的 checkpoint 命名空间，Command(graph=Command.PARENT, goto=...) 从子图跳回父图。多智能体本质上就是“每个 agent 是一个子图或一个节点”。

模式怎么做优点代价
Subagents（主 agent 调子 agent）子 agent 包装成工具，主 agent 决定调谁、传什么上下文隔离，子 agent 的中间过程不进主上下文；可以并行子 agent 无状态，用户不能直接和它对话；多一层调用
Handoffs（交接）工具调用改写一个“当前 agent”状态字段，路由到另一个 agent适合直接面对用户的多角色对话，下一轮仍由当前 agent 接着处理串行，不能并行；共享的历史越来越长
Skills（按需加载）单个 agent，需要时把某个领域的提示词和资料加载进上下文结构最简单，始终只有一个 agent 在控制加载的内容一直留在上下文里，多领域任务 token 多
Router（路由）先分类，再分发给一个或多个专门 agent，最后汇总可并行，各领域上下文互不干扰每次都要多一次路由调用；不适合多跳任务

文档里给了一个多领域任务的测算：Subagents 约 9K token，Skills 约 15K token，差别来自上下文隔离。Deep Agents 就是 Subagents 模式的成品：create_deep_agent 预装文件系统工具（ls、read_file、write_file、edit_file、glob、grep，后端支持沙箱时还有 execute）、task 工具（派生子 agent，默认带一个通用子 agent）、自动上下文压缩，可选 skills、记忆、人工审批。0.7 起不再默认带待办清单工具，默认提示词也缩短了，一轮的输入 token 从 5395 降到 1895。

自测

高频追问

LangChain 和 LangGraph 是什么关系？

同一家公司的上下两层。LangGraph 是底层编排运行时，只依赖 langchain-core；LangChain 1.x 的 create_agent 编译出来就是一张 LangGraph 图。标准的工具调用 agent 用 LangChain，自定义流程用 LangGraph，可以把 create_agent 生成的 agent 当作 LangGraph 的一个节点。

为什么有了 LCEL 还要 LangGraph？

LCEL 表达的是有向无环的流水线，agent 需要循环、条件分支、并行后汇合、中途暂停等人、崩溃后续跑。LangGraph 显式支持环和条件边，并把状态、存档、中断做进运行时，这些用 Runnable 组合很难做干净。

LangGraph 的 State 和 reducer 是什么？不配 reducer 会怎样？

State 是图的共享状态，每个字段一个通道。节点返回更新，reducer 决定更新怎么和旧值合并，默认是覆盖。同一个 super-step 里两个并行节点写同一个没配 reducer 的字段，会抛 InvalidUpdateError（“Can receive only one value per step”）。消息字段用 add_messages，按 id 追加或替换。

什么是 super-step？并行节点怎么执行？

Pregel/BSP 模型的一步：规划本步激活哪些节点，并行执行（都读本步开始时的快照），步末按 reducer 合并写入并存 checkpoint。同一步的节点看不到彼此的写入。并行来自扇出边、返回多个节点名或多个 Send；扇入用 add_edge([a, b], c) 等所有上游完成。

recursion limit 是什么？默认多少？

一次运行允许的 super-step 上限，超过抛 GraphRecursionError，防止死循环。老版本默认 25，1.0.6 起 10000，1.1.4 起 10007；create_agent 自己设为 9999。注意它数的是 super-step 而不是节点次数，__start__ 也占一步；业务上更应该用调用次数限制中间件或在状态里计数。

Send 和 Command 分别解决什么问题？

Send 解决“运行时才知道要并行几个”：路由函数返回若干 Send(node, input)，每个是独立任务、有自己的输入，用于 map-reduce。Command 解决“更新状态和决定去向写在一起”：节点返回 Command(update=..., goto=...)，还可以 graph=Command.PARENT 跳到父图，或者作为输入 Command(resume=...) 恢复中断。

checkpointer 存了什么？什么时候存？

每个 super-step 结束时存一个完整状态快照，加上下一步要执行的节点、元数据（source、step）、父 checkpoint，以及失败时已成功节点的 pending writes。按 thread_id 组织。默认 durability 是 "async"：执行下一步的同时异步写入。

短期记忆和长期记忆在 LangGraph 里怎么实现？

短期记忆是 checkpointer：同一个 thread 的状态（主要是消息历史）自动延续，太长时用裁剪、总结中间件控制。长期记忆是 Store：跨 thread，按 namespace（如用户 id）存键值，可以语义检索，由节点或工具主动读写。

interrupt() 恢复时发生了什么？有什么坑？

恢复时所在节点从头重新执行，执行到 interrupt() 时直接返回 resume 的值。坑：interrupt 前的副作用会执行两次；多个 interrupt 按顺序匹配 resume 值；不能用宽泛的 try/except 吞掉中断异常；必须配 checkpointer，并用同一个 thread_id 恢复。

时间旅行是什么？会覆盖历史吗？

用历史 checkpoint 的 config 调 invoke(None, config)：该点之前不重跑，之后重新执行；用 update_state 修改后再跑就是分叉。都会产生新的 checkpoint（source 为 fork 或 update），旧的不变，所以 thread 的历史是一棵树。

什么是 durable execution？LangGraph 怎么做到的？

长时间运行的流程在进程崩溃、部署重启后能从断点继续，而不是从头再来。LangGraph 靠每个 super-step 的 checkpoint 和 pending writes：重新用同一个 thread 调用时，已完成的步骤不重跑。节点要尽量幂等，有副作用的操作可以包在 @task 里让结果被存档。1.2 的优雅停机就是在本步结束后停下，留下可恢复的 checkpoint。

create_agent 和旧的 AgentExecutor、create_react_agent 有什么区别？

AgentExecutor 是 0.x 的黑盒循环，最早靠解析文本里的 ReAct 格式，后来也支持原生工具调用，但循环内部难以定制，已移到 langchain-classic。create_react_agent 是 LangGraph 预置的工具调用 agent，用 pre_model_hook 等参数定制，1.0 起废弃。create_agent 基于原生工具调用，编译成 LangGraph 图，用六个中间件钩子定制，结构化输出放进主循环。

中间件的执行顺序是怎样的？

middleware=[A, B, C]：before_agent、before_model 按 A、B、C 的顺序；after_model、after_agent 按 C、B、A；wrap_model_call、wrap_tool_call 是洋葱，A 在最外层，请求经过 A、B、C 到达模型，响应按 C、B、A 返回。before_*、after_* 是图里的节点，可以写 jump_to 改路由；wrap_* 是函数包装，可以改请求、重试、短路。

模型一次返回多个工具调用，create_agent 怎么执行？

每个待执行的调用生成一个 Send("tools", [call])，在同一个 super-step 里并行执行，结果作为 ToolMessage 用 add_messages 合并回状态，下一步回到模型。如果工具之间有顺序依赖，应该让模型分两轮调用，或者把它们合成一个工具。

多智能体用 supervisor 还是 handoff？

主 agent 调子 agent（supervisor / subagents）上下文隔离好、能并行，但子 agent 不直接面对用户；handoff 适合多角色直接和用户对话，串行、历史共享。先问自己是否真的需要多个 agent：很多时候单 agent 加按需加载的 skills 就够了，多 agent 会增加调用次数和调试难度。

LangGraph 在生产中要注意什么？

用 Postgres 等持久 checkpointer 并定期清理；节点幂等，副作用放在 interrupt 之后或单独节点；设置调用次数上限和节点超时；状态里不要放大对象，大文件放外部存储只存引用；用 LangSmith 或 OpenTelemetry 追踪；升级时注意 1.x 小版本里的行为变化，比如 langchain-core 1.7 的工具调用流式格式。

大家对 LangChain 的批评是什么？1.0 怎么回应的？

批评主要是抽象层太多、调试时要穿过很多层封装、版本频繁破坏性变更、文档跟不上。1.0 的回应：核心包大幅收缩，旧东西移到 langchain-classic；agent 只保留一个 create_agent，可以用中间件定制，不再是黑盒；承诺 2.0 之前不做破坏性变更。不过 langchain-core 1.7 改变工具调用的流式迭代行为，说明“1.x 不破坏”在边角上并不绝对。

2 分钟口述

答题模板

  1. 先讲关系。LangGraph 是底层编排运行时，LangChain 1.x 是上层 agent 框架，create_agent 编译成 LangGraph 图；deepagents 再往上，LangSmith 负责观测和部署。
  2. 讲 LangChain。统一的模型、消息、工具接口；LCEL 用 | 组合 Runnable，适合无环流水线；1.0 用 create_agent 加六个中间件钩子取代 AgentExecutor，before 顺序、after 逆序、wrap 洋葱。
  3. 讲 LangGraph 的图。State 加 reducer，节点返回更新，普通边、条件边、Send 扇出、Command 跳转；并行写同一字段没 reducer 会报错。
  4. 讲运行时。Pregel 式 super-step：并行执行、步末合并、存 checkpoint；recursion limit 数的是 super-step。
  5. 讲持久化带来的能力。thread 记忆、Store 长期记忆、interrupt 人工审批（恢复时节点重跑，副作用要幂等）、时间旅行、durable execution；最后提 2026 年的节点超时、错误处理、优雅停机和 MCP 并入。

常见失分点：说 LangGraph 是 LangChain 的一个模块（它是独立包，反过来 LangChain 依赖它）；说节点直接修改 state（节点返回更新，由 reducer 合并）；说 recursion limit 默认 25（1.0.6 起已改成上万）；说 interrupt 恢复时从中断的那一行继续（实际是整个节点重跑）；说时间旅行会改写历史（会产生新的 checkpoint 分支）；还在推荐 AgentExecutor 或 create_react_agent。
