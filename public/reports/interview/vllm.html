vLLM：从 PagedAttention 到 V1 引擎与 Model Runner V2

vLLM 2023 年 6 月以 PagedAttention 起家，到 2026 年 10 月已经发到 v0.32。中间经历了一次整体重写（V1 引擎）、一次执行层重写（Model Runner V2），连最初那批 PagedAttention 的 CUDA kernel 都在 v0.25 删掉了。面试问 vLLM，既会问 PagedAttention 和前缀缓存的原理，也会问 V1 改了什么、调度器怎么分 token、CUDA graph 为什么分段。本文按版本演进把这些串起来。

先给结论

30 秒背诵版

PagedAttention 管显存，前缀缓存省 prefill，统一的 token 预算做调度，CUDA graph 和异步调度压 CPU 开销

起点：KV cache 按固定大小的块（默认 16 个 token）存放，每条请求用块表把逻辑块映射到不连续的物理块，按需分配，浪费只在最后一块；块可以被多条请求共享（引用计数 + 写时复制）。论文里显存有效利用率从 20%–38% 提到 96%，吞吐是当时 FasterTransformer、Orca 的 2 到 4 倍。

前缀缓存：每个满块按“父块哈希 + 本块 token + 额外键”算哈希，命中就直接复用物理块，空闲块按 LRU 淘汰。只能复用前缀，因为一个 token 的 K、V 依赖它前面所有的 token。V1 默认开启，命中率为 0 时吞吐损失不到 1%。

V1 引擎（v0.7 试用、v0.8 默认、v0.11 删光 V0）：API server 和 EngineCore 分进程；调度器不再区分 prefill 和 decode，每步只决定“每个请求算多少个 token”，在 token 预算内统一分配，chunked prefill、前缀缓存、投机解码都是这个框架下的特例；执行层用 torch.compile 加分段 CUDA graph。

2026 年：异步调度默认开启（v0.14），CPU 调度下一步和 GPU 执行这一步重叠；Model Runner V2 去掉了 persistent batch 的重排簿记，v0.29 起对所有模型默认；KV cache 卸载发展成 CPU、磁盘、对象存储的多层结构；大规模部署靠 DP + EP、PD 分离和 KV connector。

为什么要重写成 V1 常被追问

V0 功能一个个加上去，prefill 和 decode 两套调度逻辑、多步调度、各种特性的组合互相牵制，代码越来越难改。更要紧的是 GPU 越来越快，Python 端的调度、准备输入、处理输出成了瓶颈。V1 的目标是两条：架构简单（一个统一的调度抽象），CPU 开销接近零（分进程、增量更新、缓存输入张量）。

“删除 PagedAttention”是什么意思

v0.25 删掉的是 vLLM 最初手写的 paged_attention_v1/v2 CUDA kernel，不是分块管理 KV cache 的思想。现在 FlashAttention、FlashInfer、FlashMLA 等注意力后端都原生支持按块表读写分页的 KV cache，V1 里只剩这些后端在用，旧 kernel 就没有存在的必要了。块、块表、按需分配、前缀缓存都还在。

架构

V1 架构：一个请求经过哪些组件

一个 engine step 做的事：调度器从“正在跑”的请求开始，按顺序给每个请求分 token（decode 请求 1 个，投机解码时 1 + 草稿数，没 prefill 完的请求分一段），预算有剩再从等待队列接新请求；KV cache manager 给它们分块、查前缀缓存；worker 用块表准备输入，跑一次前向和采样；新 token 回到 API server 反分词、流式返回。

内存管理

PagedAttention：像操作系统分页一样管 KV cache

早期的推理系统给每条请求预留一段连续显存，大小按最大生成长度算。问题有三个：生成多长事先不知道，预留的大部分用不上（预留浪费）；没写满的部分别人也用不了（内部碎片）；请求大小不一，释放后留下的空洞拼不起来（外部碎片）。vLLM 论文测得，当时的系统（FasterTransformer、Orca）KV cache 显存里只有 20.4% 到 38.2% 真正存了 token。PagedAttention 借鉴操作系统的虚拟内存和分页，是 vLLM 的起点。

它解决了什么

  • 按需分配：写满一块再申请下一块，不用按最大长度预留。
  • 几乎没有碎片：块大小固定，任何空闲块都能给任何请求用；浪费只在最后一块。论文里 vLLM 的有效利用率是 96.3%。
  • 共享：并行采样、beam search、相同系统提示的请求共享物理块，靠引用计数和写时复制管理。

效果是同样的显存能放更多请求，论文报告吞吐比 FasterTransformer、Orca 高 2 到 4 倍，序列越长、模型越大越明显。

代价 常被追问

  • 注意力 kernel 要先查块表，再去不连续的地址读 K、V，不能直接用要求连续内存的普通 kernel，需要专门写。
  • 块大小是个权衡：太小，块表大、访存零碎，kernel 效率低；太大，最后一块的浪费变多，共享粒度也变粗。
  • 显存不够时要抢占：把某些请求的块换出到 CPU（swap），或者直接丢掉、之后重新 prefill（recompute）。
复用

前缀缓存：相同前缀的 KV 只算一次

多条请求开头一样（同一个系统提示、同一份长文档、多轮对话的历史、Agent 每轮都带的工具定义），这一段的 KV cache 完全相同，可以只算一次，后来的请求直接跳过这段 prefill。v0.3 先做了需要手动指定前缀的版本，v0.4 换成自动前缀缓存，V1 里默认开启。

V1 的实现 块哈希

  • 哈希：每个满块的键 = 父块哈希 + 本块的 token + 额外键（LoRA ID、多模态输入的哈希、cache salt）。带父块哈希，一个块的键就隐含了它前面的全部内容。默认用 SHA-256，也可以选 xxHash。
  • 只缓存满块：没写满的最后一块不进缓存。
  • 空闲队列：所有块启动时一次性建好（块池），引用计数为 0 的块挂在一个双向链表上，淘汰时从队头拿最久没用的。请求结束时它的块按倒序放回队尾：最后一块包含的前缀最长，最不可能被复用，最先被淘汰。
  • 开销：V1 博客称命中率为 0 时吞吐损失也不到 1%，所以默认开启。

SGLang 的做法 RadixAttention

把所有缓存过的 token 序列组织成一棵基数树，新请求沿着树做最长前缀匹配，叶子按 LRU 淘汰；调度时优先处理能命中长前缀的请求，提高命中率。和 vLLM 的块哈希相比，匹配粒度是 token 而不是块。

为什么只能复用前缀 关键

第 iii 个 token 在第 2 层及以后的 K、V，依赖前面所有 token（第 1 层之后每个位置都已经混入了前文信息）；它的 K 还带着 RoPE 的绝对位置。所以两段文本只有从第一个 token 开始完全一样，KV 才相同。开头差一个 token，后面全部不能复用。

工程上的推论：固定内容放前面，变化的内容放后面；不要在系统提示里放时间戳；多轮对话和 Agent 只往后追加、不改前面的历史。各家 API 的 prompt caching 也是同一个原理。多租户场景下可以给请求加 cache salt，只有 salt 相同的请求才能共享缓存，防止通过命中时间推测别人的提示。

KV cache 本身的大小和压缩方法见 KV Cache 篇；Coding Agent 如何围绕前缀缓存设计上下文，见 Coding Agent 篇。

调度

调度器：不分 prefill 和 decode，只分 token

V0 的调度器把 prefill 和 decode 分成两种步骤，chunked prefill、前缀缓存、投机解码各自打补丁。V1 换了一个抽象：每个请求记录“已经算了多少 token”和“一共有多少 token”，每步调度就是一个字典 {请求 ID: 本步算几个 token}，总数不超过 token 预算 max_num_batched_tokens。

几种情况都是这个框架的特例

  • decode：差 1 个 token，分 1 个。
  • prefill：差整段 prompt，预算够就一次分完，不够就分一段，下一步接着分，这就是 chunked prefill。
  • 前缀缓存命中：“已经算了”的数直接从命中长度开始。
  • 投机解码：分 1 + 草稿 token 数，一次验证。

顺序和抢占

  • 先排“正在跑”的请求，再从等待队列按到达顺序接新请求，同时受 max_num_seqs 限制。
  • 每步都重新调度，请求结束立刻腾位置，新请求立刻加入：continuous batching（Orca 提出的迭代级调度）。
  • KV 块不够时，从正在跑的请求里抢占最后加入的，释放它的块，之后重新 prefill（V1 默认用重算，不再换出到 CPU）。

手算一步步怎么分

预算 16384（v0.28 起的默认值），已有 3 条请求在 decode；新来两条请求，A 的 prompt 20000 个 token，B 的 prompt 3000 个 token：

步3 条 decodeAB合计说明
1316381016384A 只分到预算剩下的部分，还差 3619；预算用完，B 等待
23361930006622A、B 都在这一步算完 prompt，并各自采样出第一个 token
331155 条请求都在 decode

decode 请求每一步都被排上，不会被长 prompt 卡住，只是第 1 步因为跟 16381 个 prefill token 一起算，会比平时慢。预算越大，prefill 越快（首 token 延迟低），但同一步的 decode 被拖得越久（出字更卡）；预算越小反过来。

交互实验

动手试：调度器怎么分 token 预算

简化版：不考虑 KV 块不够时的抢占、前缀缓存命中和投机解码；新请求在 prompt 算完的那一步采样出第一个 token，之后每步 decode 一个，生成够数量就结束；已有的 decode 请求一直不结束。最多模拟 12 步。

执行层

执行层：CUDA graph、异步调度、Model Runner V2

decode 一步只有一个 token，GPU 上的计算可能只要几毫秒，Python 端发起几百个 kernel、准备输入、调度的开销就显得很大。vLLM 执行层的演进基本都在压这部分 CPU 开销。

CUDA graph：一次录制，反复回放

把一次前向里的所有 kernel 录成一张图，之后一次提交整张图，省掉逐个启动 kernel 的开销。限制是形状必须固定，所以按若干个 batch 大小分别录制，运行时把 batch 补齐到最近的一档。

分段 CUDA graph（piecewise）

注意力的输入形状随每条请求的长度变化，而且 prefill 和 decode 混在一起，很难整张录制。V1 用 torch.compile 把模型切成几段，注意力在段与段之间按普通方式执行，其余部分录成图，这样所有注意力后端都能用。

FULL_AND_PIECEWISE（v0.11 起默认）

纯 decode 的 batch（每个请求 1 个 token，投机解码时是 1 + 草稿数）形状规整，录整张图，连注意力也包进去；混合了 prefill 的 batch 走分段图。代价是录制时间和显存都更多。PD 分离里的 decode 实例可以用 FULL_DECODE_ONLY，省掉分段图的显存。

异步调度（v0.14 起默认）

以前是“调度 → GPU 执行 → 处理输出 → 再调度”串行。异步调度让 CPU 在 GPU 执行第 nnn 步时就调度第 n+1n+1n+1 步，GPU 不再等 CPU。难点是第 n+1n+1n+1 步要用到第 nnn 步还没采样出来的 token，所以要在 GPU 上直接衔接；v0.19 起和投机解码也能零气泡重叠。

Persistent batch 和它的问题

V1 一开始的 model runner 把输入张量常驻并每步只改差异（用 NumPy 而不是 Python 循环），省掉了每步重建输入的开销。但请求进进出出时要在这个 batch 里重排、压实，簿记逻辑越来越复杂，和新特性组合时容易出错。

Model Runner V2 2026 的主线

v0.12 试验，v0.22 起对 Qwen3 稠密模型默认，v0.25 覆盖所有稠密模型，v0.29 覆盖所有模型。改动：去掉 persistent batch 的重排，块表常驻 GPU（max_model_len 很大、KV 分组很多时扩展性更好），Triton 写的采样器，更简单的 DP 和 CUDA graph 实现。之后的流水线并行、投机解码、DBO 等新特性都在 MRV2 上做。

规模化

分布式与 PD 分离

手段切的是什么什么时候用
张量并行（TP）每层的权重按头或列切到多张卡，每层要做 all-reduce单机内，模型一张卡放不下
流水线并行（PP）按层切到多张卡跨机，带宽不够做 TP；v0.16 起和异步调度一起用，吞吐提升约 30%
数据并行（DP）整个模型复制多份，各自处理不同的请求吞吐优先；MoE 模型里常和 EP 搭配：注意力做 DP，专家做 EP
专家并行（EP）MoE 的专家分到不同的卡，token 通过 all-to-all 发给对应专家DeepSeek、Kimi 这类大 MoE；有 DeepEP、EPLB（专家负载均衡）、弹性 EP
上下文并行（DCP、PCP）沿序列维度切 KV cache（decode）或切 prompt（prefill）超长上下文，单卡放不下一条请求的 KV

PD 分离和 KV connector

prefill 是计算瓶颈、决定首 token 延迟，decode 是访存瓶颈、决定每 token 延迟，放在一起会互相干扰，并行策略也没法分别调。PD 分离把两者放在不同的实例上：prefill 实例算完，把 KV cache 通过网络传给 decode 实例。vLLM 用 KV connector 接口抽象这一步，后端可以是 NIXL（RDMA）、LMCache、Mooncake 等。

KV cache 卸载：从一层到多层

GPU 放不下的 KV 块，先存到 CPU 内存（v0.19 的通用 CPU 卸载），再往下是本地文件系统、磁盘、对象存储（v0.22 到 v0.28 的多层卸载框架）。被抢占或被淘汰的前缀，下次命中时从下层读回来，比重新 prefill 便宜。卸载策略可以只存经常被复用的块。

混合内存分配器：Gemma 3 这类模型有全注意力层和滑动窗口层，Qwen3-Next、Qwen3.5 有全注意力层和线性注意力层，每类层需要的缓存不一样（滑动窗口层只需保留窗口内的块，线性注意力层是固定大小的状态）。V1 把同类的层分成一组，各组用各自的管理策略，但从同一个块池里分配。

KV cache 能分到多少显存，是启动时实测出来的：先加载权重，再用 max_num_batched_tokens 个 token 跑一次假前向，记下激活的峰值，再算上 CUDA graph 要占的显存，剩下的就是 KV cache：

MKV=U⋅MGPU−M权重−M激活峰值−MCUDA graph−M其他,N块=⌊MKVblock_size×每 token 字节数⌋M_{\text{KV}}=U\cdot M_{\text{GPU}}-M_{\text{权重}}-M_{\text{激活峰值}}-M_{\text{CUDA graph}}-M_{\text{其他}},\qquad N_{\text{块}}=\Big\lfloor\frac{M_{\text{KV}}}{\text{block\_size}\times\text{每 token 字节数}}\Big\rfloorMKV​=U⋅MGPU​−M权重​−M激活峰值​−MCUDA graph​−M其他​,N块​=⌊block_size×每 token 字节数MKV​​⌋

启动日志里会打印能放下多少个 token，以及按 max_model_len 算最多能并发多少条。按 KV Cache 篇里的算法，Llama-3.1-8B 在一张 H100 上，KV cache 大约有 50 GiB 出头，约 40 万个 token。

          max_model_len=32768, kv_cache_dtype="fp8")

# 在线服务（OpenAI 兼容接口）
# vllm serve Qwen/Qwen2.5-7B-Instruct --tensor-parallel-size 2 --max-num-batched-tokens 16384
# 简化的块管理器：块池 + 引用计数 + 前缀哈希 + LRU 空闲队列
from collections import OrderedDict

class BlockManager:
    def __init__(self, num_blocks, block_size=16):
        self.bs = block_size
        self.ref = [0] * num_blocks
        self.hash_of = [None] * num_blocks
        self.free = OrderedDict((i, None) for i in range(num_blocks))   # 队头最久没用
        self.cached = {}                                                # 哈希 -> 物理块

    def _take_free(self):
        b, _ = self.free.popitem(last=False)          # 淘汰最久没用的块
        if self.hash_of[b] is not None:               # 它若还挂着缓存，摘掉
            del self.cached[self.hash_of[b]]
            self.hash_of[b] = None
        return b

    def allocate(self, tokens):
        table, parent = [], None
        for i in range(0, len(tokens), self.bs):
            chunk = tuple(tokens[i:i + self.bs])
            full = len(chunk) == self.bs
            h = hash((parent, chunk)) if full else None   # 只有满块参与前缀缓存
            if h is not None and h in self.cached:        # 命中：复用物理块
                b = self.cached[h]
                self.free.pop(b, None)                    # 正在被用，移出空闲队列
            else:
                b = self._take_free()
                if h is not None:
                    self.cached[h], self.hash_of[b] = b, h
            self.ref[b] += 1
            table.append(b)
            parent = h
        return table                                      # 块表：逻辑块 i -> 物理块 table[i]

    def release(self, table):
        for b in reversed(table):                         # 倒序放回：长前缀的块先被淘汰
            self.ref[b] -= 1
            if self.ref[b] == 0:
                self.free[b] = None                       # 放到队尾，内容和哈希都保留，还能被命中

和真实实现的差别：真实实现边生成边追加块（这里一次性分配）；请求还在写的最后一块不会被别人共享，写满后才计算哈希；额外键里还有 LoRA、多模态、cache salt；哈希用 SHA-256 而不是 Python 的 hash；空闲块不够时由调度器抢占请求，而不是直接报错。

自测

高频追问

PagedAttention 解决了什么问题？有什么代价？

解决 KV cache 的显存浪费：按最大长度连续预留导致的预留浪费、内部碎片和外部碎片。做法是把 KV cache 切成固定大小的块（默认 16 个 token），每条请求用块表把逻辑块映射到不连续的物理块，按需分配，浪费只在最后一块；还能通过引用计数和写时复制在请求之间共享块。

代价是注意力 kernel 要通过块表间接寻址；块大小要在 kernel 效率和浪费之间权衡；显存不够时要抢占。

v0.25 把 PagedAttention 删了，那 vLLM 现在还分页吗？

还分页。删的是 vLLM 最早手写的 paged_attention_v1/v2 CUDA kernel。现在 FlashAttention、FlashInfer、FlashMLA 等后端都原生支持按块表读写分页 KV cache，V0 删除后旧 kernel 已经没有调用方。块池、块表、按需分配、前缀缓存都还在 KV cache manager 里。

V1 和 V0 最大的区别是什么？

三点。一是进程拆分：API server（分词、反分词、流式输出）和 EngineCore（调度、KV 块管理）分进程，CPU 工作和 GPU 执行重叠。二是统一调度：不区分 prefill 和 decode，每步只决定每个请求算几个 token，chunked prefill、前缀缓存、投机解码都是特例。三是执行层：worker 缓存请求状态只收增量，输入张量常驻、按差异更新，torch.compile 加分段 CUDA graph。前缀缓存因为开销降到不到 1% 而默认开启。

前缀缓存怎么做？为什么只能复用前缀？

vLLM 对每个满块用“父块哈希 + 本块 token + 额外键”算哈希，命中就复用物理块，引用计数加 1；引用为 0 的块留在 LRU 空闲队列里，内容保留，还能被命中，直到被淘汰。SGLang 用基数树做 token 粒度的最长前缀匹配。

从第 2 层开始，每个 token 的 K、V 都混入了前面所有 token 的信息，K 还带着 RoPE 的绝对位置，所以只有从开头完全一致才能复用。

chunked prefill 有什么好处和代价？

好处：长 prompt 不会独占一整步，正在 decode 的请求每步都能被排上，出字不卡；prefill 和 decode 混在一起，计算密集和访存密集的工作互补，GPU 利用率更高。

代价：一条长 prompt 要分多步算完，首 token 延迟变长；每一段都要读前面已经算好的 KV。token 预算越小，这两点越明显。

显存不够了，正在跑的请求怎么办？

抢占：从正在跑的请求里选最后加入的，释放它的 KV 块，放回等待队列，之后重新 prefill。V0 还支持把块换出到 CPU（swap），V1 默认只用重算，因为 prefill 是并行的，而且已算部分可能还能命中前缀缓存，重算往往比来回搬运便宜。现在还可以配 KV 卸载，把块存到 CPU 内存或更下层的存储。

CUDA graph 为什么要分段？FULL_AND_PIECEWISE 是什么？

CUDA graph 要求形状固定。注意力的形状随每条请求的长度变化，prefill 和 decode 还混在同一个 batch 里，所以 V1 先把注意力留在图外、其余部分分段录制，所有注意力后端都兼容。

纯 decode 的 batch 形状规整，可以把注意力也录进去，开销最低。FULL_AND_PIECEWISE 就是纯 decode 用整图、混合 batch 用分段图，v0.11 起默认，代价是更多的录制时间和显存。

异步调度解决什么问题？难点在哪？

串行时 GPU 每一步都要等 CPU 调度、准备输入、处理输出。异步调度让 CPU 在 GPU 跑第 nnn 步时就调度第 n+1n+1n+1 步。难点是第 n+1n+1n+1 步的输入依赖第 nnn 步采样出的 token，而 CPU 此时还拿不到，要在 GPU 上直接把采样结果接到下一步的输入；抢占、投机解码、结构化输出都要和这个机制兼容，所以从 v0.10 实验到 v0.14 才默认开启。

为什么要做 PD 分离？代价是什么？

prefill 是计算瓶颈、决定首 token 延迟；decode 是访存瓶颈、决定每 token 延迟。混在一起，长 prefill 会拖慢 decode，两者的并行策略、batch 大小、CUDA graph 配置也没法分别优化。分开部署后可以各自扩缩容。

代价是 KV cache 要从 prefill 实例传到 decode 实例，需要高速网络（vLLM 通过 KV connector 接 NIXL、LMCache、Mooncake）；请求量小的时候，两组实例的资源利用率可能都不高。

vLLM 启动时 KV cache 的大小是怎么确定的？

先加载权重，再用 max_num_batched_tokens 个 token 跑一次假前向测出激活峰值，加上 CUDA graph 和其他开销，用 gpu_memory_utilization 乘总显存减掉这些，剩下的全给 KV cache，按每块的字节数切成块。所以调大 max_num_batched_tokens 会让 KV cache 变小一点；OOM 时可以调小它或者调低利用率。

vLLM 和 SGLang、TensorRT-LLM 有什么区别？

三者的核心技术已经趋同：分页 KV cache、前缀缓存、continuous batching、chunked prefill、投机解码、PD 分离都有。区别更多在侧重点：vLLM 模型和硬件覆盖最广，社区最大，新模型通常首日支持；SGLang 从 RadixAttention 和结构化生成起家，调度开销低，在大规模 MoE 部署上很强；TensorRT-LLM 是 NVIDIA 的方案，和自家硬件、kernel 结合最紧。选型时以自己的模型、硬件和负载实测为准。

多租户下前缀缓存有什么安全问题？

命中缓存时首 token 明显更快，攻击者可以通过构造前缀、测量延迟，推测别人请求里有没有某段内容。vLLM 支持给请求加 cache salt，salt 混进第一个块的哈希，只有 salt 相同的请求才能共享缓存。另外哈希默认用 SHA-256，避免碰撞导致读到别人的 KV。

2 分钟口述

答题模板

  1. 一句话定位。vLLM 是开源的 LLM 推理引擎，起家于 PagedAttention：像操作系统分页一样管理 KV cache，几乎消除显存浪费，吞吐提升 2 到 4 倍。
  2. 讲内存管理。固定大小的块、块表、按需分配、引用计数和写时复制；前缀缓存按“父块哈希 + 本块 token”命中，LRU 淘汰，只能复用前缀。
  3. 讲 V1。为什么重写（V0 特性组合复杂、CPU 开销成为瓶颈）；分进程；统一调度，每步只决定每个请求算几个 token，chunked prefill 和投机解码都是特例；torch.compile 加分段 CUDA graph。
  4. 讲近期演进。V0 在 v0.11 删光；异步调度 v0.14 默认；Model Runner V2 在 v0.29 全面默认；KV 卸载变成多层；DP + EP、PD 分离、KV connector 支撑大 MoE 的大规模部署。
  5. 讲调参。gpu_memory_utilization、max_num_batched_tokens（首 token 延迟和出字流畅度的权衡）、max_num_seqs、FP8 KV cache；KV cache 大小是启动时实测激活后剩下的显存。

常见失分点：说 PagedAttention 减少了计算量（它减少的是显存浪费，靠更大的 batch 提升吞吐）；说前缀缓存能复用任意相同片段（只能是前缀）；说 V1 还分 prefill 步和 decode 步（统一按 token 调度）；说 v0.25 以后 vLLM 不分页了（删的只是旧 kernel）；说抢占时会把 KV 换出到 CPU（V1 默认重算）。
