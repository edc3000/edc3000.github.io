Pi、Codex、Claude Code：三种 Coding Agent 的设计取舍

三者的骨架是同一个 agent loop：模型提出工具调用，harness 执行，再把结果交回模型。区别在 harness 上：循环细节怎么处理、上下文里放什么、默认给几个工具、安全边界由谁来划、怎么扩展。面试常问：它们有什么区别、为什么 Pi 只有四个工具、审批弹窗算不算安全、MCP 工具太多怎么办、长会话怎么压缩。

背诵版共同骨架loop 的差别总览对比设计哲学安全模型上下文工程扩展机制动手试手撕最小 agent高频追问答题模板
先给结论

30 秒背诵版

同一个 agent loop，三种 harness 取舍：Pi 做减法，Codex 靠系统沙箱，Claude Code 开箱即用

Pi：最小内核。默认只有 read、write、edit、bash 四个工具，系统提示词很短，不弹审批，也不内置子 agent 和计划模式；要什么功能自己写 TypeScript 扩展。支持多家模型，会话存成一棵可分叉的树。安全靠把整个进程放进容器。

Codex：OpenAI 出品，Rust 写的，开源。把边界交给操作系统：sandbox mode 决定技术上能做什么，approval policy 决定什么时候停下来问。默认工作区内可写、不能联网，越界才请求批准。

Claude Code：Anthropic 出品，功能最全：几十个内置工具、子 agent、skills、hooks、plugins。权限是“规则 + 模式”，规则按 deny、ask、allow 的顺序匹配；交互默认 auto 模式，由分类器代替人审查操作。Bash 沙箱可选，只管 shell 命令。

循环细节：三者都支持一次多个工具调用、任务进行中插话（Pi 叫 steering 和 follow-up，Codex 叫 steer 和 queue）。Codex 不用服务端会话状态，每次发完整历史，靠前缀不变保住 prompt cache；Claude Code 的 Stop hook 可以否决“结束”，让它继续干。

趋势：三家在互相借鉴，功能列表越来越像。回答时重点讲默认值和边界放在哪，不要只列谁有哪个功能。

共同骨架

共同的骨架：agent loop 与 harness

Coding agent 的核心是一个循环：把上下文发给模型，模型返回文本或工具调用；有工具调用就执行，把结果追加到历史里，再发给模型；没有工具调用就结束这一轮。模型之外的部分叫 harness，三者的差别都在 harness 上。

模型是被训练成会用这个循环的：后训练阶段大量用 shell、读写文件的轨迹做 RL，所以 harness 不需要教模型“怎么当 agent”，主要负责给工具、管上下文、管安全。这也是 Pi 敢把 harness 做得很小的前提。

为什么每次都发完整历史 高频

模型接口本身无状态，或者为了零数据保留而不在服务端存历史，所以每次请求都要把整段对话发过去。第 iii 次请求的长度 LiL_iLi​ 随 iii 线性增长，一轮 nnn 次请求总共要处理

∑i=1nLi=O(n2)\sum_{i=1}^{n}L_i=O(n^2)i=1∑n​Li​=O(n2)

prompt cache 能复用之前算过的前缀，新增计算只剩每次追加的那一段，总计算量接近线性。前提是前缀一个字都不能变。

怎么保住缓存

OpenAI 介绍 Codex 循环的文章里列了会破坏缓存的操作：中途增减工具、换模型、改沙箱或审批设置、换工作目录、MCP 工具列表顺序不稳定。

Codex 的做法是不改前面的内容：权限变了就追加一条新的 developer 消息，换了目录就追加一条 user 消息。对自己写 harness 的启示：系统提示词和工具列表放最前面且保持稳定，会变的信息一律追加在后面。

一个容易被问到的细节：为什么插话和压缩都放在“一批工具执行完之后”？一个原因是主流模型接口都要求每个工具调用后面紧跟它的结果。如果在调用和结果之间塞进一条用户消息，或者把它们拆到摘要的两边，请求就不合法了。

取舍

三种设计哲学

Pi：最小内核，能力由用户加 减法

出发点是：模型已经被训练得很会用 bash 和读写文件，harness 越少越可控。作者 2025 年 11 月的文章里，系统提示词加工具定义不到 1000 token，上下文里有什么用户一清二楚，也更容易命中 prompt cache。

缺的功能用文件或扩展解决：计划写进 PLAN.md，待办写成带复选框的 TODO.md，长时间运行的进程交给 tmux。需要子 agent、计划模式、权限确认，就装扩展或自己写。

代价是开箱能力少，安全要自己负责。OpenClaw 就是在 Pi 上搭的。

Codex：把边界交给操作系统 沙箱

权限拆成两个独立的轴：sandbox mode 决定技术上能做什么（能写哪些目录、能不能联网），approval policy 决定什么时候停下来问人。默认是工作区可写加 on-request：工作区里随便改、随便跑，要联网或写工作区外才请求批准。

沙箱由系统强制执行：macOS 用 Seatbelt，Linux 和 WSL2 用 bubblewrap，Windows 有原生沙箱。云端任务跑在隔离容器里。好处是 agent 在边界内可以长时间不打扰人地跑。

Claude Code：开箱即用的完整 harness 加法

内置工具多，功能全：子 agent、skills、hooks、plugins、任务列表、计划模式、定时任务。复杂工作流不用自己搭。

权限是“规则 + 模式”：规则写成 Bash(npm run *) 这样的模式，按 deny、ask、allow 的顺序匹配；没匹配到的由模式决定要不要问。auto 模式用后台分类器代替人审查命令和网络请求。沙箱是可选项，只包住 shell 命令。

趋同：功能越来越像 趋势

Pi 早期明确不做 MCP，现在内置了，但默认不把 MCP 工具直接声明给模型；也支持 skills。Codex 加了 hooks、skills、plugins、子 agent 和自动审查。Claude Code 在 macOS、Linux 上去掉了 Glob、Grep，改用 Bash 搜索，又加了沙箱。

真正的差别在默认值：默认给几个工具、默认在不在沙箱里、默认问不问人、默认上下文里放多少东西。

必考

安全模型：边界由谁来划

Coding agent 的风险来自两处：模型自己犯错（比如删错目录），和 prompt injection（文件、网页、命令输出里藏着指令，模型照做了）。防御要回答一个问题：如果模型这一步是错的或被操纵的，最多能造成多大损失？

Claude Code 的交互会话从 v2.1.283 起默认是 auto 模式，Manual 模式（配置值 default）每个工具第一次用都要确认。Codex 已经去掉了旧的 untrusted 审批策略。

为什么审批弹窗不算安全边界 高频

  • 审批疲劳：一次任务几十上百个确认，人很快就会习惯性点同意。
  • 看不到组合效果：弹窗一次只看一条命令。先写一个脚本、再执行它，每一步单看都没问题。
  • 看不懂：一长串管道命令，人未必比模型更清楚它会做什么。

Pi 的文档直接写明：看记录、信任项目、检查改动，都不构成安全边界。安全只能来自限制进程能碰到的文件、凭证、进程和网络。

三者把边界放在哪

Pi：放在 agent 外面。整个进程跑在容器或虚拟机里，只挂载任务需要的目录，凭证用短期、范围小的。

Codex：放在命令执行这一层。每条命令都在系统沙箱里跑，审批只在越界时才出现，所以审批次数少，每次都值得看。

Claude Code：规则和模式管所有工具，沙箱管 shell。文档特别说明：文件工具、MCP 服务器、hooks 都跑在沙箱外面，所以开了沙箱也还要配权限规则。

Claude Code 的规则怎么匹配

按 deny、ask、allow 的顺序，第一个匹配的生效，和规则写得多具体无关：宽的 deny 规则 Bash(aws *) 会挡住 aws s3 ls，即使另有一条 allow 规则。命令里的每个子命令都要过 deny 和 ask，包括子 shell 和命令替换里的。

PreToolUse hook 也绕不过 deny 和 ask 规则。deny 规则在 bypassPermissions 模式下也生效。

Codex 的两个轴怎么组合

sandbox mode 有三档：read-only、workspace-write、danger-full-access。approval policy 主要是 on-request（越界时问）和 never（从不停下来问）。

两者独立：never 加 workspace-write 适合 CI，不会卡在等人，但也出不了沙箱；“完全放开”是 danger-full-access 加 never。approvals_reviewer 可以把审批交给一个审查 agent，但这只换了审批的人，不会放大沙箱。沙箱外允许哪些命令，可以用 Starlark 写 rules。

上下文工程

上下文工程：工具、指令文件与压缩

工具：少而通用 vs 多而专用

工具定义每次请求都要带上，占上下文，工具多了模型还容易选错。Pi 只给四个，搜索、git、测试都走 bash。Claude Code 工具多，但专用工具能做更细的权限控制（比如按路径限制 Read），输出格式也更稳定。

两边在靠近：Claude Code 在 macOS、Linux 上把 Glob、Grep 去掉了，让模型直接用 bash 里的 find、grep。

改文件：字符串替换 vs 补丁

Pi 和 Claude Code 的 edit 是精确字符串替换：给出旧文本和新文本，旧文本必须和文件内容逐字一致。Claude Code 还要求它在文件里只出现一次，否则报错，让模型多带几行上下文再试。好处是不用行号，文件被别人改过也不会改错位置。

Codex 用 apply_patch，一种类似 diff 的补丁格式，一次能增删改多个文件。OpenAI 的模型专门训练过这种格式。选哪种取决于模型训练时用的是哪种。

指令文件：怎么加载

Codex 从仓库根目录走到当前目录，每层取一个 AGENTS.md（有 AGENTS.override.md 就用它），按顺序拼接，越靠近当前目录的越靠后、优先级越高，总长默认截断在 32 KiB。

Claude Code 启动时加载上级目录的 CLAUDE.md，子目录里的等用到那个目录再加载；可以用 @path 导入其他文件，建议单个文件不超过 200 行。Pi 两种文件名都认，不管项目是否受信任都会加载。

压缩：长会话怎么办

Pi 的自动压缩在 Cctx>W−RC_{\text{ctx}}>W-RCctx​>W−R 时触发，CctxC_{\text{ctx}}Cctx​ 是当前上下文长度，WWW 是窗口大小，RRR 默认 16384。从最新消息往回保留约 20k token，更早的交给模型写成结构化摘要；原始消息仍留在会话文件里，只是不再发给模型。

Claude Code 也是自动压缩，可以 /compact 指定重点；压缩后会从磁盘重新加载 CLAUDE.md，只在对话里说过的指令可能丢失。Codex 可以在本地压缩，也可以交给 Responses 接口在服务端压缩。

Pi 的会话是一棵树 特色

会话存成 JSONL，每条记录有自己的 id 和父节点 id。从之前某一步继续就是在树上开一个新分支，原来的分支还在；当前分支决定下一次请求带哪些历史。切换分支时可以把离开的那条分支总结成摘要带过来。这样试错不会污染主线：走偏了就回到分叉点重来，而不是在上下文里堆一堆失败的尝试。

扩展

扩展机制：MCP、Skills、Hooks、子 agent

MCP：工具多了怎么办

一个 MCP 服务器常有几十个工具，定义全部塞进上下文很贵。Pi 作者 2025 年测过：Playwright MCP 约 13.7k token，Chrome DevTools MCP 约 18k token。三种解法：

  • 延迟加载：开局只给工具名，模型用搜索工具找到后再加载定义。Claude Code 的 tool search 默认开启，Pi 叫 deferred。
  • codemode：只给模型一个“写脚本”的工具，模型在脚本里调用 MCP 工具、过滤结果，只有脚本的输出进上下文。Pi 的 MCP 默认这样做，脚本跑在没有文件和网络权限的 QuickJS 沙箱里。
  • 不用 MCP：给模型一个命令行工具和它的 README，用 bash 调用。

Skills：按需加载的说明书

一个 skill 是一个目录，里面有 SKILL.md 和附带文件。开局只把每个 skill 的简短描述放进上下文，模型判断用得上时才读全文，附带的参考文档用到再读。三者都支持。

和 MCP 的区别：MCP 提供新的能力（工具），skill 提供做事的方法（指令和脚本），通常还是用已有的 bash、read 去执行。skill 便宜，因为只有描述常驻上下文。

Hooks：确定性的规则

skill、MCP 都要模型自己决定用不用；hook 是 harness 在固定事件上一定会执行的代码，比如工具调用前、调用后、压缩前、会话开始。适合“每次改完文件都跑格式化”“禁止改某个目录”这类不能靠模型自觉的规则。

Claude Code 和 Codex 用配置文件声明 hook，调用外部命令；Pi 用扩展监听事件，tool_call 事件可以改参数或直接拦截，权限确认就可以这样实现。

子 agent：隔离上下文的代价

好处：子 agent 有自己的上下文窗口，读几十个文件、跑一堆搜索，最后只把结论交回主对话，主上下文保持干净；多个子 agent 还能并行。

代价：每个子 agent 都要自己读一遍上下文，token 消耗更多；主 agent 看不到子 agent 的过程，出错不好排查。Pi 作者正是因为“看不到它在干什么”而不内置，需要时让 pi 通过 bash 再起一个 pi。

交互实验

动手试：MCP 工具占多少上下文

假设接了 NNN 个 MCP 工具，每个工具定义平均 ttt token，这一轮实际用到 kkk 个，每次调用返回 rrr token。三种接法这一轮占用的上下文：

C全量=Nt+kr,C延迟=Nc+kt+kr,Ccodemode=T+kt+fkrC_{\text{全量}}=Nt+kr,\qquad C_{\text{延迟}}=Nc+kt+kr,\qquad C_{\text{codemode}}=T+kt+fkrC全量​=Nt+kr,C延迟​=Nc+kt+kr,Ccodemode​=T+kt+fkr

ccc 是只列工具名时每个工具的开销，取 15；TTT 是 codemode 工具本身的说明，取 1200；fff 是脚本过滤后留给模型的比例。这几个常数是示意值。

工具定义调用结果

prompt cache 能让重复带上的工具定义变便宜，但它们仍然占着上下文窗口，也会分散模型的注意力。codemode 还有一个没算进去的开销：模型要多写一段脚本，有时还要先搜索工具再调用，多一轮请求。

手撕

手撕：最小 coding agent

Pi 的核心大致就是下面这些：一个循环、四个工具、一份简短的系统提示词。llm 代表任意支持工具调用的模型接口，返回文本和工具调用列表。

import json, subprocess, pathlib

def read(path, offset=0, limit=2000):
    lines = pathlib.Path(path).read_text().splitlines()
    return "\n".join(lines[offset:offset + limit])

def write(path, content):
    p = pathlib.Path(path); p.parent.mkdir(parents=True, exist_ok=True)
    p.write_text(content); return f"wrote {len(content)} chars"

def edit(path, old_text, new_text):
    s = pathlib.Path(path).read_text()
    n = s.count(old_text)
    if n != 1:                                    # 必须唯一匹配，否则让模型补充上下文
        return f"error: old_text matched {n} times"
    pathlib.Path(path).write_text(s.replace(old_text, new_text)); return "ok"

def bash(command, timeout=120):
    r = subprocess.run(command, shell=True, capture_output=True, text=True, timeout=timeout)
    out = r.stdout + r.stderr
    return out[-30000:] + f"\n[exit {r.returncode}]"   # 截断过长输出，只保留结尾

TOOLS = {"read": read, "write": write, "edit": edit, "bash": bash}
agents_md = pathlib.Path("AGENTS.md")
SYSTEM = "You are a coding agent. Use the tools to inspect and change files.\n" \
         + (agents_md.read_text() if agents_md.exists() else "")

def run(messages):
    while True:
        text, calls = llm(SYSTEM, messages, tools=TOOLS)     # 模型返回文本和工具调用
        messages.append({"role": "assistant", "content": text, "tool_calls": calls})
        if not calls:
            return text                                     # 没有工具调用：本轮结束
        for c in calls:
            if not allowed(c):                              # 权限检查：规则、审批或分类器
                result = "denied by user"
            else:
                try:
                    result = TOOLS[c["name"]](**json.loads(c["arguments"]))
                except Exception as e:
                    result = f"error: {e}"                  # 报错也交回模型，让它自己修
            messages.append({"role": "tool", "id": c["id"], "content": result})
        if token_count(messages) > WINDOW - RESERVE:
            messages = compact(messages)                    # 摘要旧消息，保留最近一段

要点：工具报错不抛给用户，而是作为结果交回模型；输出要截断；allowed 和 compact 是三者差别最大的两个函数。生产级实现还要处理流式输出、中途插话、取消、并行工具调用和 prompt cache。

自测

高频追问

Pi、Codex、Claude Code 最大的区别是什么？

agent loop 是一样的，区别在 harness 的默认值。Pi 做减法：四个工具、短提示词、不弹审批，靠容器隔离，其余功能由扩展提供。Codex 靠系统沙箱：命令在 Seatbelt、bubblewrap 等沙箱里跑，默认工作区可写、断网，越界才问。Claude Code 功能最全：工具多，子 agent、skills、hooks 都内置，权限用规则加模式，auto 模式由分类器审查。另外 Pi 支持多家模型，Codex、Claude Code 主要配自家模型。

三者的 agent loop 有什么不同？

骨架相同：请求、回复、执行工具、写回结果，直到回复里没有工具调用。不同在细节：

  • 请求内容：Codex 不用 previous_response_id，每次把完整历史发给 Responses API，推理内容加密回传；权限、目录变化以追加消息的方式表达，保住缓存前缀。Pi 每次从会话树的当前分支重建上下文，扩展还能改写它。
  • 工具执行：一条回复里的多个调用，Pi 默认先逐个检查再并发执行；Claude Code 按批执行，整批完成才发下一次请求；Codex 对 MCP 工具要服务器声明可并行才并发。
  • 插话：都分两种，一种插进当前任务（Pi 的 steering、Codex 的 steer、Claude Code 的排队消息），一种等任务结束（Pi 的 follow-up、Codex 的 queue）。插入点在一批工具执行完之后。
  • 结束：默认都是没有工具调用就结束；Claude Code 的 Stop hook 可以否决，让模型继续，/goal 就是这样实现的。
Pi 只有四个工具，够用吗？为什么这样设计？

够用。bash 能做搜索、git、跑测试、装依赖，前沿模型在后训练时大量练过这些。工具少的好处：系统提示词短，省上下文、容易命中缓存；模型不会在一堆相似工具里选错；用户清楚上下文里有什么。Terminal-Bench 上也能看到，很简单的 harness 不一定比复杂的差。

代价是专用工具的好处没了：比如按路径做权限控制、结构化的输出、对大文件的分页读取。Pi 的 read 自带分页，这一点没丢。

审批弹窗为什么不算安全边界？应该怎么做？

三个原因：次数多了人会习惯性点同意；每次只看一条命令，看不到“先写脚本再执行”这种组合；复杂命令人也看不懂。再加上 prompt injection，文件、网页、命令输出都可能操纵模型。

真正的边界是限制进程能接触到的东西：在容器或虚拟机里跑，或者用系统沙箱（Codex 的默认做法），只给需要的目录、关掉不需要的网络、用短期凭证。审批应该少而有意义：只在越过边界时出现。

Codex 的 sandbox mode 和 approval policy 是什么关系？

两个独立的轴。sandbox mode 是技术限制：read-only 只能读，workspace-write 能写工作区、默认断网，danger-full-access 没有限制。approval policy 决定什么时候停下来问：on-request 在要越过沙箱时问，never 从不问。

默认 workspace-write 加 on-request。CI 里常用 never，跑不出沙箱的命令直接失败，不会卡住。把审批交给审查 agent（auto_review）只是换了审批人，不会放大沙箱。

Claude Code 的 auto 模式和 bypassPermissions 有什么区别？

auto 模式不弹窗，但每个命令、网络请求执行前都会经过一个后台分类器，检查是否符合用户的请求，有风险的会被拦下。bypassPermissions 完全跳过检查，文档要求只在容器或虚拟机这种隔离环境里用。两者都受 deny 规则约束。

MCP 工具太多，上下文不够用怎么办？

三种办法。延迟加载：开局只给工具名，用搜索找到再加载定义，Claude Code 默认如此。codemode：只暴露一个写脚本的工具，模型在脚本里调 MCP、过滤结果，只有输出进上下文，Pi 的 MCP 默认如此，适合结果很大、只需要一小部分的场景。第三种是干脆不用 MCP，给一个命令行工具和 README，让模型用 bash 调。

Skills 和 MCP 有什么区别？

MCP 提供新的工具，每个工具的定义都要进上下文（除非延迟加载）。skill 是一份按需读取的说明书加脚本：开局只放一句描述，用得上时才读 SKILL.md 全文，执行时通常还是用 bash、read 这些已有工具。所以 skill 很便宜，适合沉淀“怎么做某件事”；MCP 适合接入需要鉴权、有状态的外部服务。

子 agent 有什么用？Pi 为什么默认不带？

主要用来隔离上下文：让子 agent 去读大量文件、做调研，只把结论交回来，主对话不被中间过程塞满；独立任务还能并行。代价是 token 更多，而且主 agent 和用户看不到子 agent 做了什么，出错难排查。Pi 作者看重可观察性，所以不内置；需要时可以装扩展，或让 pi 通过 bash 起一个新的 pi 进程。

长会话怎么压缩？压缩会丢什么？

接近窗口上限时，保留最近一段消息，把更早的交给模型写成摘要，用摘要替换旧消息。Pi 在剩余空间不到 16384 token 时触发，保留最近约 20k token，摘要是结构化的，会记录改过哪些文件；原始消息留在会话文件里。

会丢细节：早期对话里给的指令、试错的过程、具体报错。所以持久的规则要写进 AGENTS.md 或 CLAUDE.md，Claude Code 压缩后会从磁盘重新加载它们。

改文件用字符串替换和 apply_patch 各有什么优缺点？

字符串替换（Pi、Claude Code）：模型给出要替换的原文和新文本，原文必须逐字匹配，不依赖行号，文件被并发修改时也不容易改错位置；缺点是每处修改都要带足上下文，一次只改一处。

apply_patch（Codex）：补丁格式，一次可以改多个文件、多个位置，也能新建、删除文件；格式更复杂，写错容易应用失败。关键是和模型训练时用的格式一致，OpenAI 的模型专门训练过这种补丁格式。

会话中途换模型会遇到什么问题？

各家的思考内容格式不一样，有的还加密或带签名，不能直接发给别家模型。Pi 作者 2025 年的文章里介绍的做法是：切换厂商时把思考内容转成普通文本，包在 <thinking> 标签里，他也承认这并不完美。另外工具调用的格式要互相转换，prompt cache 会失效，新模型也可能不习惯前一个模型留下的风格。

让你从零写一个 coding agent，最少需要什么？

一个循环加四个工具（读、写、改、执行命令）就能跑。然后按重要性补：输出截断和错误回传、加载 AGENTS.md、上下文压缩、会话持久化、取消和中途插话、权限或沙箱、prompt cache。先保证上下文干净、可观察，再加功能。

2 分钟口述

答题模板

  1. 共同点。三者都是同一个 agent loop：模型提出工具调用，harness 执行并回填结果。循环细节有差别：并行执行工具、两种插话队列、压缩时机、Stop hook 能否否决结束；Codex 每次发完整历史，靠稳定前缀保缓存。
  2. Pi。做减法：四个工具、短提示词、不弹审批，靠容器隔离；子 agent、计划模式等由扩展提供；支持多家模型，会话是可分叉的树。
  3. Codex。靠系统沙箱：sandbox mode 管能做什么，approval policy 管什么时候问；默认工作区可写、断网，越界才问。Rust 写的，开源。
  4. Claude Code。开箱即用：工具多，子 agent、skills、hooks、plugins 都内置；权限是规则加模式，auto 模式用分类器审查；沙箱可选，只管 shell。
  5. 取舍。可控性和上下文干净（Pi），安全边界强、可以长时间无人值守（Codex），功能全、上手快（Claude Code）。三家在趋同，差别主要在默认值。

常见失分点：把审批弹窗当成安全边界；以为 Claude Code 默认开了沙箱（默认关闭，而且只管 shell 命令）；说 Pi 不支持 MCP（早期不支持，现在内置，默认用 codemode 方式）；以为工具越多越强。
