KV Cache：显存账、访存瓶颈与压缩

KV cache 的原理一句话就能说完，面试真正考的是后面的工程问题：一个模型的 KV cache 有多大、为什么 decode 慢在读显存而不是算力、GQA 和 MLA 各省了哪一项、量化和驱逐有什么代价。本文用一台 H100 跑 Llama-3.1-8B 把账算一遍。

先给结论

30 秒背诵版

用显存换计算；大小正比于层数、KV 头数、头维度、精度和 token 数；decode 被它的读取速度卡住

是什么：自回归生成时，因果 mask 保证前面 token 的 K、V 不会因为后面的 token 改变，所以每层把算过的 K、V 存下来，新 token 只算自己的 q,k,vq,k,vq,k,v，和缓存里的所有 K、V 做注意力，再把自己的 k,vk,vk,v 追加进去。Q 用完就扔，不用缓存。生成 nnn 个 token 的计算量从 O(n2)O(n^2)O(n2) 次投影降到 O(n)O(n)O(n) 次。

多大：每 token=2⋅L⋅g⋅dh⋅b\text{每 token}=2\cdot L\cdot g\cdot d_h\cdot b每 token=2⋅L⋅g⋅dh​⋅b 字节（LLL 层数、ggg KV 头数、dhd_hdh​ 头维度、bbb 每个数的字节数），再乘上下文长度和 batch。Llama-3.1-8B 每 token 128 KiB，32K 上下文一条请求 4 GiB，可能比权重还大。

为什么是瓶颈：decode 每步每条请求都要把自己的整个 KV cache 读一遍，每个读进来的数只做几次乘加，算术强度约等于 h/gh/gh/g，和 batch 无关，所以注意力部分永远是访存瓶颈；长上下文时读 KV cache 的时间超过读权重。

怎么优化：按公式逐项压：ggg（MQA、GQA）、dhd_hdh​（MLA 存低秩潜向量）、bbb（FP8、INT4 量化）、token 数（滑动窗口、驱逐）、LLL（跨层共享、混合线性注意力）。多条请求的 KV cache 怎么分配、复用和调度，是推理引擎的事，见 vLLM 篇。

原理

为什么能缓存，缓存什么

能缓存的前提：因果 mask 关键

第 iii 个位置只看得到 1..i1..i1..i，所以在每一层，位置 iii 的隐状态只依赖前面的 token，后面追加 token 不会改变它，它的 ki,vik_i,v_iki​,vi​ 也就不会变。BERT 这类双向模型做不到：加一个 token，前面所有位置的表示都会变。

为什么不缓存 Q

注意力里是“当前位置的 qqq”去查“所有位置的 k,vk,vk,v”。过去位置的 qqq 只在算过去位置的输出时用过一次，那些输出已经算完、也不会再变，以后再也用不到。

生成 nnn 个 token不用 KV cache用 KV cache
第 ttt 步的投影和 FFN对前 ttt 个 token 全部重算，O(t d2)O(t\,d^2)O(td2)只算新 token，O(d2)O(d^2)O(d2)
第 ttt 步的注意力t×tt\times tt×t 的分数矩阵，O(t2d)O(t^2d)O(t2d)1×t1\times t1×t 的一行，O(t d)O(t\,d)O(td)
总计（每层）O(n2d2+n3d)O(n^2d^2+n^3d)O(n2d2+n3d)O(n d2+n2d)O(n\,d^2+n^2d)O(nd2+n2d)
额外显存无O(n d)O(n\,d)O(nd)，随长度线性增长

KV cache 本质是用显存换计算。它没有消掉注意力的平方项：第 ttt 步仍然要和 ttt 个 key 做点积，只是消掉了重复计算。矩阵乘法、RoPE、注意力的基础见 Transformer 篇。

核心追问

为什么 decode 卡在访存，batch 救不了注意力

判断一个操作是算力瓶颈还是访存瓶颈，看算术强度：每从显存读 1 字节，做多少次浮点运算。H100 的 BF16 稠密算力约 989 TFLOPS，带宽 3.35 TB/s，两者之比约 295。强度低于这个数，就是在等显存。

线性层：batch 能摊薄
强度≈2⋅B⋅N2⋅N=B  FLOPs/字节\text{强度}\approx\frac{2\cdot B\cdot N}{2\cdot N}=B\ \ \text{FLOPs/字节}强度≈2⋅N2⋅B⋅N​=B  FLOPs/字节

每个 BF16 权重（2 字节）读进来一次，batch 里每条请求都用它做一次乘加（2 FLOPs）。BBB 越大越划算，BBB 到几百才接近算力瓶颈。

注意力：batch 摊不薄
强度≈2⋅(h/g)2=hg  FLOPs/字节\text{强度}\approx\frac{2\cdot(h/g)}{2}=\frac{h}{g}\ \ \text{FLOPs/字节}强度≈22⋅(h/g)​=gh​  FLOPs/字节

每条请求的 KV cache 只属于它自己，读进来的每个 K 元素只被同组的 h/gh/gh/g 个 query 头各用一次。和 BBB 无关：MHA 是 1，Llama-3.1-8B 的 GQA 是 4，离 295 差得很远。

所以每步 decode 的时间可以用“要读多少字节 ÷ 带宽”估一个下界：

tstep≳权重字节+∑i=1B第 i 条请求的 KV cache 字节显存带宽t_{\text{step}}\gtrsim\frac{\text{权重字节}+\sum_{i=1}^{B}\text{第 }i\text{ 条请求的 KV cache 字节}}{\text{显存带宽}}tstep​≳显存带宽权重字节+∑i=1B​第 i 条请求的 KV cache 字节​

batch 小、上下文短

主要时间花在读权重上。加 batch 几乎不增加每步时间，吞吐线性上涨，所以推理服务都要尽量把 batch 做大。

batch 大、上下文长 现实情况

KV cache 的读取量随 B×sB\times sB×s 增长，很快超过权重，每步时间跟着变长。这时缩小 KV cache 既能放下更多请求，又能直接缩短每步时间，是双重收益。

MLA 在推理时把 WUKW^{UK}WUK 吸收进 query 一侧，所有头共享同一个潜向量，相当于 g=1g=1g=1、h=128h=128h=128，算术强度比 GQA 高一个数量级，这也是 DeepSeek 选 MLA 的原因之一。

MLA 为什么要解耦 RoPE 常被追问

没有 RoPE 时，q⊤k=q⊤WUKcKVq^\top k=q^\top W^{UK}c^{KV}q⊤k=q⊤WUKcKV，可以把 WUKW^{UK}WUK 合进 query 一侧，直接和缓存的 cKVc^{KV}cKV 做点积。RoPE 在 qqq 和 kkk 之间插了一个和位置有关的旋转矩阵，WUKW^{UK}WUK 就合并不进去了。所以 MLA 把 key 拆成两部分：不带位置的部分走低秩压缩，另外单独算一个 64 维、所有头共享的 RoPE key 一起缓存。

为什么不干脆缓存每层的输入

缓存 xxx（ddd 维）再现算 K=xWKK=xW_KK=xWK​、V=xWVV=xW_VV=xWV​，MHA 下能省一半显存，但每步要对整段上下文重做投影，计算量回到 O(s d2)O(s\,d^2)O(sd2)。GQA 下 2g dh2g\,d_h2gdh​ 已经小于 ddd（Llama-3.1-8B 是 2048 对 4096），缓存 K、V 反而更小。MLA 可以看成这条思路的改进版：缓存一个比 ddd 小得多的潜向量，再靠矩阵吸收避免重算。

问题做法
每条请求预留连续显存，碎片和浪费严重PagedAttention：KV cache 切成固定大小的块，用块表映射到不连续的物理块，按需分配

手撕

代码：带 KV cache 的 GQA decode 一步

# 单层注意力的 decode 一步。为简单起见假设 batch 里所有请求长度相同
# x: [B, d] 当前这一个 token 的输入；cache_k, cache_v: [B, g, max_len, dh]；pos: 当前位置
def attn_decode(x, cache_k, cache_v, pos, Wq, Wk, Wv, Wo, h, g, dh):
    B = x.shape[0]
    q = (x @ Wq).view(B, h, 1, dh)
    k = (x @ Wk).view(B, g, 1, dh)
    v = (x @ Wv).view(B, g, 1, dh)
    q, k = rope(q, pos), rope(k, pos)                 # 缓存的是旋转之后的 k
    cache_k[:, :, pos] = k[:, :, 0]                   # 追加到缓存
    cache_v[:, :, pos] = v[:, :, 0]
    K = cache_k[:, :, :pos + 1].repeat_interleave(h // g, dim=1)   # [B, h, pos+1, dh]
    V = cache_v[:, :, :pos + 1].repeat_interleave(h // g, dim=1)
    att = (q @ K.transpose(-1, -2)) / dh ** 0.5       # [B, h, 1, pos+1]，缓存里只有过去，不需要 mask
    o = att.softmax(-1) @ V                           # [B, h, 1, dh]
    return o.reshape(B, h * dh) @ Wo

# 生成循环：prefill 一次填满前 n 个位置，之后每步只喂一个 token
logits = model.prefill(prompt_ids, cache)            # prompt_ids: [B, n]
for pos in range(n, n + max_new):
    tok = sample(logits[:, -1])                       # [B]
    logits = model.decode(tok, cache, pos)           # 每层调用一次 attn_decode

真实实现和这段代码的差别：repeat_interleave 会把 K、V 复制 h/gh/gh/g 份，真正的 kernel 直接让同组的 query 头读同一份；请求长度各不相同，缓存按块存放，kernel 通过块表寻址（PagedAttention）；缓存的是加过 RoPE 的 kkk，所以前缀复用要求位置也一致。

自测

高频追问

KV cache 是什么？为什么只缓存 K、V，不缓存 Q？

自回归生成时，把每层算过的 K、V 存下来，新 token 只算自己的 q,k,vq,k,vq,k,v，和缓存做注意力，再把 k,vk,vk,v 追加进去。能缓存是因为因果 mask：后面的 token 不会改变前面位置的表示。

当前步只需要当前位置的 qqq，去查所有位置的 k,vk,vk,v。过去位置的 qqq 只用于算过去位置的输出，那些输出已经算完、不会再变，所以不用存。

给一个模型，KV cache 怎么算？

每 token 2⋅L⋅g⋅dh⋅b2\cdot L\cdot g\cdot d_h\cdot b2⋅L⋅g⋅dh​⋅b 字节，再乘序列长度和 batch。注意用的是 KV 头数 ggg 而不是 query 头数。Llama-3.1-8B：2×32×8×128×2=1282\times32\times8\times128\times2=1282×32×8×128×2=128 KiB，32K 一条 4 GiB。Llama-2-7B 是 MHA，每 token 512 KiB，是它的 4 倍。

为什么 decode 是访存瓶颈？加大 batch 能解决吗？

decode 每步每条请求只处理一个 token，线性层是向量乘矩阵，读一次权重只做 BBB 次乘加；注意力要把这条请求的整个 KV cache 读一遍，每个数只被 h/gh/gh/g 个 query 头用一次。两者的算术强度都远低于 GPU 的算力带宽比（H100 约 295）。

加 batch 能摊薄权重的读取，但摊不薄 KV cache：每条请求的 KV cache 是独立的，batch 越大要读的越多。所以长上下文、大 batch 时，读 KV cache 成了主要开销。

MQA、GQA、MLA 分别是怎么省的？

MQA 所有 query 头共享 1 组 K、V，缩小 hhh 倍，效果有损；GQA 分成 ggg 组，缩小 h/gh/gh/g 倍，效果接近 MHA，可以从 MHA 模型把 KV 头平均池化后少量训练得到。

MLA 不减头数，而是把 K、V 压成一个低秩潜向量（DeepSeek-V3 是 512 维）加一个 64 维的共享 RoPE key 来缓存，推理时把上投影矩阵吸收到 query 和输出投影里。DeepSeek-V2 论文报告比 DeepSeek 67B 的 KV cache 少了 93.3%。

MLA 为什么要单独处理 RoPE？

矩阵吸收依赖 q⊤k=q⊤WUKcKV=(WUK⊤q)⊤cKVq^\top k=q^\top W^{UK}c^{KV}=(W^{UK\top}q)^\top c^{KV}q⊤k=q⊤WUKcKV=(WUK⊤q)⊤cKV。RoPE 在 qqq 和 kkk 上各乘一个和位置有关的旋转矩阵，WUKW^{UK}WUK 和旋转矩阵不能交换，就吸收不进去了。所以 MLA 让压缩部分不带位置信息，另外算一个所有头共享的 RoPE key 和压缩向量一起缓存，两部分的点积相加。

KV cache 量化时，K 和 V 为什么要分开处理？

K 有少数通道的数值特别大（离群通道），而且这些通道在不同 token 上是固定的，所以 K 按通道量化，每个通道一个缩放系数，离群值就不会拉坏其他通道。V 没有这种通道结构，而且注意力输出是 V 按 token 的加权和，按 token 量化误差更可控。这是 KIVI 的做法，它把 KV cache 压到 2-bit。FP8 不用这么讲究，基本无损。

StreamingLLM 为什么要保留开头几个 token？

只保留最近窗口的 KV，一旦开头的 token 被挤出去，困惑度会突然飙升。原因是模型会把大量注意力分给开头几个 token，它们像一个“垃圾桶”（attention sink），用来放 softmax 必须分出去、又没有地方可放的注意力。保留开头 4 个 token 加最近的窗口，就能稳定地处理无限长的输入流。但它不能记住窗口外的内容，不等于扩展了上下文。

KV cache 和 FlashAttention 是什么关系？

两者正交。FlashAttention 解决的是 prefill 和训练时 n×nn\times nn×n 注意力矩阵的显存读写，分块计算、不写回完整矩阵，算的东西不变。KV cache 解决的是生成时的重复计算。decode 阶段 query 只有一个，FlashAttention 原来的并行方式填不满 GPU，所以有了 Flash-Decoding：沿 KV cache 的序列维度切分并行，最后合并。

2 分钟口述

答题模板

  1. 一句话定位。KV cache 是自回归推理用显存换计算：因果 mask 保证过去的 K、V 不变，存下来以后每步只算新 token。
  2. 报大小。每 token 2Lgdhb2Lgd_h b2Lgdh​b 字节，乘长度和 batch；举 Llama-3.1-8B 每 token 128 KiB、32K 一条 4 GiB 的例子，说明长上下文时它比权重还大。
  3. 讲瓶颈。decode 是访存瓶颈；线性层靠 batch 摊薄权重读取，注意力的算术强度约 h/gh/gh/g，和 batch 无关，所以 KV cache 既限制了能放多少请求，又拖慢每一步。
  4. 讲压缩。按公式逐项：GQA 压 ggg，MLA 存低秩潜向量（解耦 RoPE），FP8 和 KIVI 压字节数，滑动窗口和 StreamingLLM 压 token 数，跨层共享和混合线性注意力压层数。
  5. 讲系统。引擎层面用 PagedAttention 分块管理、前缀缓存复用相同前缀、continuous batching 和 PD 分离做调度（展开见 vLLM 篇）；kernel 层面用 Flash-Decoding 沿序列维度并行。

常见失分点：说 KV cache 也存 Q；用 query 头数算 GQA 模型的 KV cache；说 KV cache 把注意力降到了线性（每步仍要和全部历史做点积，只是不重复计算）；说加大 batch 能解决注意力的访存瓶颈。
